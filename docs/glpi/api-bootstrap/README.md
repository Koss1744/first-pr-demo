# api-bootstrap — создание объектов Релиза 1 через REST API GLPI

**Статус: подготовлено к выполнению.** Прямого доступа к https://sd.hofi.su
у автора нет — инстанс находится в локальной сети заказчика. Скрипты
запускает администратор со своей машины (или с сервера GLPI).

Скрипты — не замена руководству. Они закрывают ту часть Релиза 1, где
ручной ввод в интерфейсе даёт много одинаковых объектов и много опечаток:
15 категорий, 6 SLA, 5 сегментов календаря, поля шаблона, шаблоны писем.
Всё, что требует решения человека (профили, правила, получатели уведомлений),
делается руками по [`../setup-release1.md`](../setup-release1.md).

---

## 1. Что создаётся скриптом

| Шаг | Объекты GLPI | Кол-во | Источник данных |
|---|---|---|---|
| `groups` | `Group` | 2 или 4 | `data/groups.json` |
| `categories` | `ITILCategory` | 4 родителя + 15 листьев | `data/categories.json` |
| `calendar` | `Calendar`, `CalendarSegment`, `Holiday`, `Calendar_Holiday` | 1 + 5 + 7 + 7 | `data/calendar.json` |
| `sla` | `SLM`, `SLA` | 1 + 6 | `data/sla.json` |
| `ticket-template` | `TicketTemplate` + обязательные/скрытые/предзаполненные поля | 1 + ~11 | `data/ticket-template.json` |
| `notification-templates` | `NotificationTemplate`, `NotificationTemplateTranslation` | 5 + 5 | `data/notification-templates.json` |

Плюс два шага только на чтение: `preflight` (состояние инстанса, cron,
носители Super-Admin) и `verify` (сверка результата с эталоном).

## 2. Что скрипт сознательно НЕ делает

Это решения, а не пробелы. Каждый из этих объектов при ошибке либо
невосстановим, либо бьёт по живым людям.

| Объект | Почему руками |
|---|---|
| **Профили** (`Profile`, `ProfileRight`) | Профиль создаётся клонированием штатного (кнопка «Клонировать»). Собранный по битам через API профиль невозможно сверить с «как из коробки» при обновлении GLPI. Шаг 9 руководства |
| **Правила** (`RuleTicket`, `RuleRight`, `RuleMailCollector`) | Правило = критерии + действия + порядок + флаг остановки. Порядок критичен, и проверяется каждое правило на тестовой заявке по одному. Массовая заливка правил скрывает именно то, что нужно увидеть. Шаги 20–21 |
| **Уведомления** (`Notification`, `NotificationTarget`) | Получатель задаётся числовой константой, состав которых различается между версиями. Ошибка здесь — письма не тем людям, и «откатить» отправленное письмо нельзя. Шаг 18 |
| **Сущности** (`Entity`) | Переименование корневой сущности и создание дочерней — две операции в интерфейсе, зато видно, что именно меняется. Шаг 5 |
| **Почта и LDAP** | Зона `glpi-integrator`: [`../integrations/mail-collector.md`](../integrations/mail-collector.md), [`../integrations/ldap-ad.md`](../integrations/ldap-ad.md) |
| **Состав групп** | Поимённые списки даёт руководитель ИТ. Скрипт не знает, кто вышел в отпуск |

## 3. Требования

* Python 3.8+ (только стандартная библиотека, ничего ставить не нужно).
* Включённый REST API: **Настройка → Основная конфигурация → вкладка «API»**
  → «Включить REST API» = Да, «Включить вход с использованием токена» = Да.
* App-Token (там же, «Добавить клиента API») и персональный токен учётной
  записи (**Администрирование → Пользователи → <учётка> → Ключ API**).
* Учётная запись с профилем `super-Admin` — на время bootstrap. После
  завершения Релиза 1 токен отзывается.
* Сетевой доступ к инстансу: он снаружи недоступен, запускать изнутри.

## 4. Запуск

```bash
cd docs/glpi/api-bootstrap
cp .env.example .env          # заполнить реальными значениями, не коммитить
set -a; . ./.env; set +a

# 0. офлайн-проверка самих скриптов, GLPI не нужен
python3 selftest.py

# 1. состояние инстанса (ничего не меняет)
python3 bootstrap.py --confirm sd.hofi.su --steps preflight

# 2. ПЛАН: что будет создано. Это dry-run, он и есть режим по умолчанию
python3 bootstrap.py --confirm sd.hofi.su --steps all --groups-variant two

# 3. применение — только после того, как план прочитан глазами
#    и снят бэкап БД (шаг 3 руководства)
python3 bootstrap.py --confirm sd.hofi.su --steps all --groups-variant two --apply

# 4. сверка результата
python3 bootstrap.py --confirm sd.hofi.su --steps verify
```

Шаги можно выполнять по одному — порядок обязателен и совпадает с порядком
в списке: `groups → categories → calendar → sla → ticket-template →
notification-templates`. Календарь создаётся **до** SLA: SLA ссылается на
календарь, и подмена календаря задним числом не пересчитывает сроки уже
открытых заявок.

### Ключи

| Ключ | Назначение |
|---|---|
| `--confirm HOSTNAME` | обязателен; должен совпасть с хостом из `GLPI_URL`. Имя набирается руками — это защита от запуска не на том контуре |
| `--apply` | применить. Без него **не уходит ни один запрос на запись** |
| `--steps` | список шагов через запятую или `all` |
| `--groups-variant two\|four` | две группы (SD-L1 + IT-ALL) или четыре. См. раздел «Две группы или четыре» в руководстве |
| `--entity N` | сущность, в которой создаются объекты (по умолчанию 0 — корневая) |
| `--max-changes N` | предохранитель, по умолчанию 120 |
| `--allow-update` | разрешить доводить уже существующие объекты до эталона. Без ключа расхождения только показываются |

## 5. Защита от ошибки

Работа идёт под `super-Admin`: у этой учётной записи нет «нельзя». Поэтому
ограничения встроены в сам скрипт.

1. **Dry-run по умолчанию.** Транспортный уровень отказывается выполнять
   `POST`/`PUT`/`DELETE`, пока не передан `--apply`. Это не проверка в начале
   функции, которую легко обойти, — это отказ в методе `_request`.
2. **Белый список типов** (`ALLOWED_ITEMTYPES` в `glpi_client.py`).
   Пользователи, профили, правила, заявки в него не входят: скрипт физически
   не может их изменить, даже если ошибиться в данных.
3. **Подтверждение инстанса** — имя хоста набирается вручную в `--confirm`.
4. **Лимит изменений за запуск** (`--max-changes`, по умолчанию 120). Ровно
   столько объектов и создаёт Релиз 1; при выходе за лимит скрипт
   останавливается с объяснением, а не «доделывает до конца».
5. **`DELETE` запрещён** в `bootstrap.py` на уровне транспорта. Удаляет
   только `rollback.py` и только по журналу.
6. **Существующие объекты не правятся** без `--allow-update`; расхождение
   показывается, но не применяется.
7. **Журнал каждой операции** — `logs/ledger-<дата>-<режим>.jsonl`.
8. **Идемпотентность.** Перед созданием объект ищется по ключам сопоставления
   (имя + родитель). Повторный запуск даёт только `skip`. Проверено
   в `selftest.py`, пункт 4.

## 6. Откат

```bash
# план отката (ничего не удаляет)
python3 rollback.py --confirm sd.hofi.su --ledger logs/ledger-20260922-121403-apply.jsonl

# выполнение
python3 rollback.py --confirm sd.hofi.su --ledger logs/ledger-20260922-121403-apply.jsonl --apply

# откат одного шага
python3 rollback.py --confirm sd.hofi.su --ledger <журнал> --only-step categories --apply
```

`rollback.py` удаляет **только** объекты с `action=create` из указанного
журнала, в обратном порядке (дети раньше родителей), сверяя имя объекта с
записью в журнале. Если объект переименован или id занят другим объектом —
он пропускается с предупреждением.

Если в системе уже есть заявки, откат требует `--force`: удаление категорий
и групп рвёт ссылки в существующих заявках. В этом случае правильный путь —
не удалять, а деактивировать объекты и завести новые.

**Откат, который скрипт не сделает** (профили, правила, уведомления,
настройки сущности): пошагово в [`../config-log.md`](../config-log.md),
колонка «Как откатить».

## 7. Секреты

Только переменные окружения (`.env`, не в git). В коде и в JSON —
плейсхолдеры `<APP_TOKEN>`, `<USER_TOKEN>`. Токены не передаются аргументами
командной строки: аргументы видны в `ps` и остаются в истории оболочки.
После закрытия Релиза 1 персональный токен учётной записи bootstrap
перевыпускается или удаляется.

## 8. Проверка результата без API

`sql/verify-release1.sql` — только `SELECT`, 17 проверок: cron, календарь,
SLA, категории без группы, дубликаты, профили, носители Super-Admin, порядок
правил, антипетля «отправитель ≠ сборщик», очередь уведомлений.

```bash
mysql -u <DB_USER> -p <DB_NAME> < sql/verify-release1.sql
```

## 9. Отличия GLPI 11.x

Скрипты написаны под **GLPI 10.x** (`/apirest.php`). До запуска подтвердите
версию — `preflight` печатает её первой строкой и предупреждает, если видит 11.x.

* В 11.x рядом со старым REST API появляется новый (`/api.php/v2`) с
  авторизацией OAuth2 вместо `App-Token` + `user_token`. Старый API в ветке
  11 ещё присутствует, но считается устаревшим; если он отключён политикой —
  скрипты потребуют переписывания слоя аутентификации в `glpi_client.py`
  (остальная логика не меняется).
* Часть `itemtype` и номера полей шаблона могут отличаться. Поэтому номера
  полей не захардкожены: они резолвятся через `GET /listSearchOptions/Ticket`
  и сверяются с ожидаемыми, расхождение печатается.
* Классический упрощённый интерфейс в 11.x заменён каталогом услуг и
  конструктором форм — шаблон заявки остаётся, но форма пользователя
  строится иначе. Проверку «пользователь не видит поле Влияние» в 11.x
  выполняйте в интерфейсе, а не по наличию записи в скрытых полях.
