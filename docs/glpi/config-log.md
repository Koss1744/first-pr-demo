# Журнал изменений конфигурации GLPI — HOFI

Инстанс: https://sd.hofi.su · Ведёт: администратор GLPI (`glpi-admin`)
Связанные документы: [`setup-release1.md`](setup-release1.md),
[`requirements.md`](requirements.md), [`api-bootstrap/`](api-bootstrap/)

---

## Зачем этот файл

Конфигурацию GLPI нельзя положить в git: она живёт в базе данных. Значит
единственный способ узнать **что, когда, кем и зачем** было изменено — вести
журнал руками. Без него через три месяца невозможно ответить на вопрос
«почему заявки из почты попадают на первую линию, а не на ИТ» иначе как
раскопками в интерфейсе.

Журнал — это ещё и план отката. Колонка «Как откатить» заполняется **до**
выполнения изменения, а не после. Если непонятно, как откатить, — значит
изменение не продумано и выполнять его рано.

Ведение журнала — приёмочный критерий Релиза 1 (**A-20**).

## Правила ведения

1. **Запись создаётся в день изменения.** «Потом допишу» не работает:
   через неделю не вспомнить, какое из полей было изменено.
2. **Одна запись — одно осмысленное изменение.** Не «настроил SLA», а
   «создан SLM `HOFI Base 5x9` и 6 SLA» с перечнем.
3. **Пишется значение «было» и «стало».** Запись без «было» бесполезна для
   отката.
4. Статус записи: `подготовлено` → `выполнено` → при необходимости
   `откачено` или `отменено`. Запись **не удаляется никогда**, даже если
   изменение откатили: откаченное изменение — тоже история.
5. **Реальных учётных данных, паролей, токенов и ключей API в журнале быть
   не должно.** Только плейсхолдеры (`<SUPPORT_MAILBOX>`, `<APP_TOKEN>`) и
   ссылка на то, где значение хранится. См. раздел «Секреты».
6. Изменения, сделанные скриптом, всё равно фиксируются здесь: журнал
   `api-bootstrap/logs/*.jsonl` привязан к конкретному инстансу и в git не
   попадает, а этот файл переживает пересоздание инстанса.
7. Изменения конфигурации в рабочее время после запуска — только по
   согласованию с владельцем системы (руководителем ИТ, RE-Q6).

## Шаблон записи

Копировать целиком, заполнять все поля. Прочерк ставится осознанно, пустых
полей быть не должно.

```markdown
### CL-0NN · <Краткое название изменения>

| | |
|---|---|
| **Дата (план / факт)** | 2026-09-__ / — |
| **Статус** | подготовлено / выполнено / откачено / отменено |
| **Кто** | <ФИО или роль> |
| **Шаг руководства** | setup-release1.md, шаг N |
| **Требование** | R1-XXX-NN, критерий A-NN |
| **Объект GLPI** | `Тип` — конкретные имена/id |
| **Раздел интерфейса** | Точный путь в меню |
| **Было** | значение до изменения |
| **Стало** | значение после изменения |
| **Зачем** | 1–2 строки: какую проблему решает |
| **Как проверить** | конкретная проверка, а не «посмотреть, что работает» |
| **Как откатить** | пошагово; если откат невозможен — написать это прямо |
| **Риск при откате** | что сломается/потеряется |
```

## Полный откат Релиза 1

Применяется, если конфигурация повреждена настолько, что пошаговый откат
дороже восстановления. **Останавливает работу системы на время
восстановления** — согласуется с владельцем системы.

1. Отключить приёмник почты и уведомления (CL-020, CL-024), чтобы во время
   восстановления не создавались новые заявки и не уходили письма.
2. Снять свежий дамп текущего состояния — даже испорченного. Он понадобится,
   чтобы понять, что пошло не так, и чтобы вернуть заявки, созданные после
   последнего бэкапа.
3. Восстановить БД из дампа (процедура и проверка — CL-003):

   ```bash
   gunzip -c /var/backups/glpi/glpi-<STAMP>.sql.gz | mysql -u <DB_USER> -p <DB_NAME>
   ```

4. Восстановить каталог `files` из соответствующего архива — иначе вложения
   в заявках будут ссылаться в пустоту.
5. Проверить: `sql/verify-release1.sql`, вход администратора, число заявок.
6. Включить обратно приёмник и уведомления.
7. **Заявки, созданные между бэкапом и восстановлением, будут потеряны.**
   Поэтому перед массовыми изменениями конфигурации снимается свежий дамп —
   это отдельная строка в чек-листе, а не подразумеваемое действие.

## Откат объектов, созданных скриптом

```bash
cd docs/glpi/api-bootstrap
python3 rollback.py --confirm sd.hofi.su --ledger logs/ledger-<дата>-apply.jsonl          # план
python3 rollback.py --confirm sd.hofi.su --ledger logs/ledger-<дата>-apply.jsonl --apply  # выполнение
```

Откатываются только объекты из журнала запуска: группы, категории, календарь
и нерабочие дни, SLM и SLA, шаблон заявки, шаблоны уведомлений. Профили,
правила, уведомления и настройки сущности скриптом не создавались — их откат
описан в колонке «Как откатить» соответствующих записей выше.
