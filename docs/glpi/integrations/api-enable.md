# Включение REST API и автоматизация настройки Релиза 1

**Статус:** подготовлено к выполнению. Прямого доступа к инстансу
https://sd.hofi.su у автора документа нет; все команды выполняет
администратор заказчика из внутреннего периметра.

**Контекст:** заказчик готов предоставить учётную запись с профилем
`Super-Admin`. Часть настройки Релиза 1 (категории, группы, SLA, шаблоны
уведомлений) дешевле создавать скриптами, чем руками в интерфейсе: это
воспроизводимо, версионируемо и откатывается по журналу операций.

**Версия:** GLPI 10.x (`apirest.php`, API v1). Отличия 11.x — в разделе 8.

**Предупреждение, определяющее весь документ:** скрипт под `Super-Admin`
без режима предварительного просмотра — это массовое изменение продуктивной
конфигурации без возможности посмотреть, что именно произойдёт. Раздел 7
обязателен к выполнению, а не к ознакомлению.

## 1. Включение API в GLPI 10.x

Путь: **Настройка → Общие → вкладка «API»**.

| Параметр | Ключ конфигурации | Значение для HOFI | Комментарий |
|---|---|---|---|
| URL API | `url_base_api` | `<GLPI_URL>/apirest.php` | подставляется автоматически из URL инстанса; проверить, что домен совпадает с рабочим (`https://sd.hofi.su`) |
| Включить Rest API | `enable_api` | Да | без этого любой запрос вернёт 404 |
| Вход с учётными данными | `enable_api_login_credentials` | **Да на время настройки, Нет после** | разрешает `initSession` по логину/паролю |
| Вход с внешним токеном | `enable_api_login_external_token` | Нет (на старте) | вход по `user_token` пользователя; включать, когда появятся постоянные интеграции |

Ниже на этой же странице — список **клиентов API**. Клиент — это не
пользователь, а «приложение»: он даёт `App-Token` и ограничение по IP.

Создать клиента (кнопка «Добавить клиента API»):

| Поле | Значение | Комментарий |
|---|---|---|
| Название | `Release1 automation (<ФИО администратора>)` | понятное имя: по нему потом искать записи в журнале |
| Активен | Да | выключается одним кликом — это ваш «рубильник» |
| Журналирование подключений | «Исторические данные» или «Журналы» | без журнала нельзя восстановить, что делал скрипт |
| Фильтр доступа: диапазон IPv4 (начало/конец) | `<AUTOMATION_IP>` — `<AUTOMATION_IP>` | **один адрес**: начало = конец = адрес рабочей станции администратора |
| IPv6 | пусто | если не используется |
| Токен приложения (App-Token) | сгенерировать кнопкой | это `<APP_TOKEN>` |

Клиент по умолчанию («full access from anywhere», без ограничения IP) для
работ Релиза 1 **не используется**: он выдан на весь интернет и не отличим в
журналах от любой другой интеграции. Если он существует и не нужен —
деактивировать.

Рекомендация: **отдельный клиент API на каждую задачу/интеграцию**
(автоматизация Релиза 1, будущий обмен со смежной системой, мониторинг).
Тогда компрометация или отзыв одного токена не ломает остальные.

## 2. Требования к сетевому доступу

| Откуда | Куда | Протокол/порт | Комментарий |
|---|---|---|---|
| Рабочая станция администратора внутри периметра `<AUTOMATION_IP>` | `<GLPI_URL>` (`sd.hofi.su`) | HTTPS/443 | основной и предполагаемый вариант |
| Сервер приложений/CI (если появится) | `<GLPI_URL>` | HTTPS/443 | требует отдельного клиента API и своего диапазона IP |

Существенные моменты:

1. **Инстанс может быть недоступен извне контура.** Это нормальная и
   предпочтительная конфигурация. В этом случае скрипты выполняются **с
   рабочей станции администратора внутри периметра**, а не из внешних сред
   (включая среду, где готовились эти материалы).
2. Если между клиентом и GLPI стоит обратный прокси или WAF, он должен
   пропускать заголовки `App-Token` и `Session-Token`. Их «срезание» —
   типовая причина ошибки `ERROR_APP_TOKEN_PARAMETERS_MISSING` при верном
   токене.
3. IP, который GLPI видит в запросе, — это IP, дошедший до PHP. За прокси
   это может быть адрес прокси, а не рабочей станции: диапазон в клиенте API
   нужно задавать по тому адресу, который реально фиксируется (проверяется
   опытным путём: неверный IP даёт `ERROR_WRONG_APP_TOKEN_PARAMETER`).
4. Сертификат `<GLPI_URL>` должен быть доверенным на машине, откуда идут
   запросы. `curl -k` в скриптах не использовать: это отключает проверку и
   для всех последующих вызовов.

## 3. Смоук-тест

Все значения — плейсхолдеры, пароли берутся из переменных окружения и не
записываются ни в скрипт, ни в историю команд.

```bash
# --- подготовка окружения (значения вводятся вручную, не хранятся в файлах) ---
export GLPI_URL="https://sd.hofi.su"
read -rs -p "App-Token: "  GLPI_APP_TOKEN; export GLPI_APP_TOKEN; echo
read -r  -p "Логин GLPI: " GLPI_LOGIN;     export GLPI_LOGIN
read -rs -p "Пароль GLPI: " GLPI_PASSWORD; export GLPI_PASSWORD; echo
```

```bash
# --- 1. initSession: Basic-аутентификация + App-Token ---
SESSION_TOKEN=$(curl -sS -X GET "$GLPI_URL/apirest.php/initSession" \
  -H "Content-Type: application/json" \
  -H "App-Token: $GLPI_APP_TOKEN" \
  -u "$GLPI_LOGIN:$GLPI_PASSWORD" \
  | python3 -c 'import sys,json; print(json.load(sys.stdin)["session_token"])')

echo "Сессия получена: ${SESSION_TOKEN:0:6}…"
```

`curl -u` передаёт заголовок `Authorization: Basic ...`. Логин и пароль **не
передаются в URL**: строка запроса попадает в журналы веб-сервера и в
историю shell.

```bash
# --- 2. проверочные GET ---
# активные сущности текущей сессии
curl -sS -X GET "$GLPI_URL/apirest.php/getActiveEntities" \
  -H "App-Token: $GLPI_APP_TOKEN" -H "Session-Token: $SESSION_TOKEN"

# список категорий заявок (первые 20)
curl -sS -X GET "$GLPI_URL/apirest.php/ITILCategory?range=0-19" \
  -H "App-Token: $GLPI_APP_TOKEN" -H "Session-Token: $SESSION_TOKEN"

# профиль текущей сессии - убедиться, что это действительно Super-Admin
curl -sS -X GET "$GLPI_URL/apirest.php/getActiveProfile" \
  -H "App-Token: $GLPI_APP_TOKEN" -H "Session-Token: $SESSION_TOKEN"
```

```bash
# --- 3. killSession: обязательный шаг, даже если что-то упало ---
curl -sS -X GET "$GLPI_URL/apirest.php/killSession" \
  -H "App-Token: $GLPI_APP_TOKEN" -H "Session-Token: $SESSION_TOKEN"

unset SESSION_TOKEN GLPI_PASSWORD GLPI_APP_TOKEN
```

Как читать результат:

| Ответ | Значение |
|---|---|
| `{"session_token":"…"}` | API включён, вход по учётным данным разрешён, App-Token принят, IP разрешён |
| `ERROR_LOGIN_WITH_CREDENTIALS_DISABLED` | не включён «Вход с учётными данными» (раздел 1) |
| `ERROR_APP_TOKEN_PARAMETERS_MISSING` | заголовок `App-Token` не дошёл (проверить прокси) |
| `ERROR_WRONG_APP_TOKEN_PARAMETER` | неверный токен **или** IP вне диапазона клиента API |
| `ERROR_GLPI_LOGIN` (401) | неверные учётные данные или учётка неактивна |
| HTTP 404 | API выключен или неверный путь (`/apirest.php`) |
| HTML вместо JSON | запрос ушёл не на тот хост / перехвачен порталом авторизации |
| `ERROR_SESSION_TOKEN_INVALID` на шаге 2 | сессия истекла (тайм-аут) или уже была закрыта |

Шаблон скрипта, который всегда закрывает сессию:

```bash
#!/usr/bin/env bash
set -euo pipefail

: "${GLPI_URL:?}" "${GLPI_APP_TOKEN:?}" "${GLPI_LOGIN:?}" "${GLPI_PASSWORD:?}"
DRY_RUN="${DRY_RUN:-1}"     # 1 = только показать, что будет сделано
LOG="glpi-api-$(date +%Y%m%d-%H%M%S).log"

SESSION_TOKEN=""
cleanup() {
  if [ -n "$SESSION_TOKEN" ]; then
    curl -sS -X GET "$GLPI_URL/apirest.php/killSession" \
      -H "App-Token: $GLPI_APP_TOKEN" -H "Session-Token: $SESSION_TOKEN" >/dev/null || true
    echo "session closed" | tee -a "$LOG"
  fi
}
trap cleanup EXIT INT TERM     # сессия закрывается и при ошибке, и при Ctrl+C
```

`trap` здесь не украшение: незакрытые сессии висят до тайм-аута, накапливаются
в таблице сессий и мешают понять по журналу, что именно делал скрипт.

## 4. Что создаётся через API, а что — только в интерфейсе

Правило: через API управляются **объекты-записи** (строки в таблицах GLPI).
**Глобальные настройки** (то, что лежит в конфигурации инстанса) через
`apirest.php` не задаются — их меняют в интерфейсе либо консольной командой
на сервере (`php bin/console config:set <ключ> <значение>`).

### 4.1. Создаётся через API

| Объект Релиза 1 | Itemtype | Комментарий |
|---|---|---|
| Категории заявок | `ITILCategory` | иерархия через `itilcategories_id`; создавать сверху вниз |
| Группы (поддержки и организационные) | `Group` | + `Group_User` для состава |
| Пользователи (локальные: подрядчики, сервисные) | `User`, `UserEmail` | AD-пользователи приходят синхронизацией, не через API |
| Профили | `Profile` | набор прав задаётся десятками полей — проще клонировать в интерфейсе, потом править точечно |
| Назначение профилей и сущностей | `Profile_User` | массовая выдача прав локальным учёткам |
| Сущности | `Entity` | вместе с параметрами уведомлений сущности (`notification_subject_tag`) |
| Расположения | `Location` | |
| Уровни обслуживания | `SLM`, затем `SLA` / `OLA` | сначала контейнер `SLM`, потом привязанные соглашения |
| Правила эскалации/назначения | `Rule`, `RuleCriteria`, `RuleAction` | создаются тремя связанными запросами; проверять результат в интерфейсе |
| Шаблоны уведомлений | `NotificationTemplate` + `NotificationTemplateTranslation` | текст шаблона — во втором объекте |
| Подписки на уведомления | `Notification`, `Notification_NotificationTemplate` | |
| Типы обращений, источники, категории задач | `RequestType`, `TaskCategory` | |
| Шаблоны заявок | `TicketTemplate` и связанные `…MandatoryField` / `…PredefinedField` | |
| Типы документов (для вложений из почты) | `DocumentType` | напрямую влияет на приём вложений, см. `mail-collector.md` 6.3 |
| Чёрный список адресов | `Blacklist` | часть защиты от петель |
| Почтовый коллектор | `MailCollector` | технически создаётся (пароль шифруется при сохранении), но требует передачи `<IMAP_PASSWORD>` через API — см. 4.3 |
| Каталог LDAP | `AuthLDAP` | то же замечание про `<LDAP_BIND_PASSWORD>` |
| Заявки (для нагрузочных/приёмочных тестов) | `Ticket`, `ITILFollowup` | тестовые данные удобно наливать и удалять скриптом |

Базовые операции:

```bash
# создать
curl -sS -X POST "$GLPI_URL/apirest.php/ITILCategory" \
  -H "Content-Type: application/json" \
  -H "App-Token: $GLPI_APP_TOKEN" -H "Session-Token: $SESSION_TOKEN" \
  -d '{"input": {"name": "Печать и МФУ", "itilcategories_id": 0, "is_helpdeskvisible": 1}}'

# изменить
curl -sS -X PUT "$GLPI_URL/apirest.php/ITILCategory/<ID>" \
  -H "Content-Type: application/json" \
  -H "App-Token: $GLPI_APP_TOKEN" -H "Session-Token: $SESSION_TOKEN" \
  -d '{"input": {"comment": "Обновлено скриптом настройки Релиза 1"}}'

# удалить в корзину (без force_purge - обратимо)
curl -sS -X DELETE "$GLPI_URL/apirest.php/ITILCategory/<ID>" \
  -H "App-Token: $GLPI_APP_TOKEN" -H "Session-Token: $SESSION_TOKEN"
```

`force_purge=true` в Релизе 1 не использовать: безвозвратное удаление
лишает возможности откатиться штатными средствами.

### 4.2. Только в интерфейсе (или консолью на сервере)

| Настройка | Где | Почему не через API |
|---|---|---|
| Настройки API (раздел 1) | Настройка → Общие → API | глобальная конфигурация инстанса |
| Параметры SMTP-уведомлений | Настройка → Уведомления | глобальная конфигурация (`smtp_*`, `from_email`, …) |
| Включение уведомлений | Настройка → Уведомления | глобальная конфигурация |
| Настройки аутентификации: порядок источников, действие при удалении пользователя из LDAP (`user_deleted_ldap`) | Настройка → Аутентификация | глобальная конфигурация |
| Анонимные заявки (`use_anonymous_helpdesk`) | Настройка → Общие → Помощь | глобальная конфигурация |
| Автодействия: частота, режим GLPI/CLI, включение | Настройка → Автодействия | правится в интерфейсе; менять расписание скриптом — плохая идея |
| Импорт пользователей и групп из AD | Администрирование → Пользователи → Связь с каталогом LDAP | отдельный процесс; для регулярного запуска — `bin/console ldap:synchronize_users` |
| Права внутри профиля (матрица чекбоксов) | Администрирование → Профили | десятки взаимосвязанных полей; ошибка здесь стоит доступа в систему |
| Ключ шифрования GLPI | файл `config/glpi.key` | не конфигурация, а файл на сервере |

Итоговая доля автоматизации для Релиза 1: **справочники и структура (категории,
группы, SLA, шаблоны, типы документов) — скриптами; интеграции с секретами и
глобальные настройки — руками в интерфейсе**. Это примерно 70 % объёма
рутинной работы аналитика/администратора и почти ничего из настроек,
влияющих на доступ.

### 4.3. Про объекты с паролями (`MailCollector`, `AuthLDAP`)

Создать их через API можно: GLPI шифрует `passwd` / `rootdn_passwd`
собственным ключом при сохранении. Но при этом секрет проходит через
командную строку и журналы скрипта. Рекомендация для Релиза 1: эти два
объекта создаются **в интерфейсе**, а скриптом при необходимости правятся
только непарольные поля (частота, папки, флаги).

## 5. Работа под `Super-Admin`: правила безопасности

1. **Отдельный App-Token для автоматизации** и отдельный клиент API
   (раздел 1). Не переиспользовать токен мобильного приложения, плагина или
   другой интеграции.
2. **Ограничение по IP — обязательно.** Диапазон = один адрес рабочей
   станции администратора. Клиент API без ограничения IP при включённом
   входе по логину/паролю означает, что подбор пароля `Super-Admin` можно
   вести откуда угодно.
3. **«Вход с учётными данными» включается на время работ и выключается
   после.** Это одна галочка, и она — основная причина, по которой API
   становится вектором атаки.
4. **`killSession` обязателен**, в том числе при аварийном завершении
   (см. `trap` в разделе 3).
5. **Журналирование включено** у клиента API («Исторические данные» или
   «Журналы»), плюс собственный журнал скрипта: дата, операция, itemtype, ID
   созданного объекта, HTTP-код. Без списка созданных ID откат превращается
   в ручное сравнение.
6. **Учётная запись автоматизации — именная и временная.** Оптимально:
   отдельная локальная учётка GLPI `svc.api` c профилем `Super-Admin`,
   выданным **на время работ**, с фиксированной датой окончания
   («Действителен до»). Работать под личной учёткой администратора — значит
   смешать в журнале действия человека и скрипта.
7. **Токен — секрет.** Не в git, не в `crontab`, не в аргументах команды.
   При подозрении на утечку: клиент API → «Перегенерировать токен».
8. **Скрипты — в репозитории, значения — снаружи.** Сам скрипт полезно
   хранить в `docs/glpi/` или отдельном каталоге проекта: он и есть
   документация к тому, что было создано. Значения — из переменных окружения.
9. **Никаких массовых DELETE с `force_purge`** и никаких операций «по
   диапазону ID» без предварительного вывода списка.
10. **Перед запуском любого пишущего скрипта на продуктиве — дамп БД GLPI.**
    Это единственный универсальный откат.

## 6. Журнал операций

Минимальный формат (CSV/JSONL рядом со скриптом, не в git при наличии в нём
имён реальных объектов):

```
timestamp;operation;itemtype;input_name;http_code;created_id
2026-09-15T10:12:04;POST;ITILCategory;Печать и МФУ;201;42
2026-09-15T10:12:05;POST;ITILCategory;Печать и МФУ > Замена картриджа;201;43
```

Журнал нужен для трёх вещей: откат (раздел 7.3), приёмка (что именно создано)
и разбор инцидента («кто добавил эту категорию»). Плюс к нему — встроенная
история GLPI: вкладка «Исторические данные» у каждого объекта и
Администрирование → Журналы.

## 7. Режим предварительного просмотра (dry-run) и откат

### 7.1. Почему без dry-run нельзя

Скрипт под `Super-Admin` не ограничен правами: ошибка в теле запроса
создаёт не то и не там (частый случай — создание объектов в корневой
сущности вместо целевой), а ошибка в цикле создаёт это сотни раз. В
интерфейсе такой ошибке мешает скорость набора руками; у скрипта этого
предохранителя нет.

### 7.2. Как устроен dry-run

Обязательный минимум для любого пишущего скрипта Релиза 1:

- переменная `DRY_RUN` со значением по умолчанию **1** (безопасное);
- при `DRY_RUN=1` выполняются **только** `initSession`, чтения (`GET`) и
  печать плана изменений; ни одного `POST`/`PUT`/`DELETE`;
- план печатается в том же виде, что и журнал: операция, itemtype, ключевые
  поля, найденный существующий объект (создание или обновление);
- предварительная проверка на дубли: перед созданием — поиск объекта с тем
  же именем в той же сущности;
- запуск с изменениями — явный: `DRY_RUN=0 ./script.sh`, с подтверждением
  в консоли.

```bash
apply() {               # apply <METHOD> <PATH> <JSON>
  local method="$1" path="$2" body="$3"
  if [ "$DRY_RUN" = "1" ]; then
    echo "[DRY-RUN] $method $path $body" | tee -a "$LOG"
    return 0
  fi
  local code
  code=$(curl -sS -o /tmp/resp.json -w '%{http_code}' -X "$method" "$GLPI_URL/apirest.php/$path" \
    -H "Content-Type: application/json" \
    -H "App-Token: $GLPI_APP_TOKEN" -H "Session-Token: $SESSION_TOKEN" \
    ${body:+-d "$body"})
  echo "$(date -Is);$method;$path;$code;$(cat /tmp/resp.json)" >> "$LOG"
  [ "$code" -lt 400 ] || { echo "ОШИБКА $code на $method $path"; return 1; }
}
```

Порядок применения на продуктиве:

1. `DRY_RUN=1` — прочитать план целиком глазами.
2. Дамп БД.
3. `DRY_RUN=0` на **одном** объекте (например, одной категории).
4. Проверка результата в интерфейсе.
5. `DRY_RUN=0` на всём наборе.
6. Сверка журнала и приёмка.

### 7.3. Откат

| Уровень | Действие |
|---|---|
| Немедленно остановить любой доступ | Настройка → Общие → API → клиент API → «Активен: Нет» (или `enable_api` = Нет — отключает API целиком) |
| Отозвать токен | клиент API → перегенерировать `App-Token` |
| Закрыть доступ по паролю | «Вход с учётными данными» = Нет |
| Откатить созданные объекты | по журналу операций: `DELETE /<itemtype>/<id>` для каждого созданного ID **в обратном порядке создания** (дочерние раньше родительских) |
| Откатить изменённые объекты | вкладка «Исторические данные» объекта показывает прежние значения; возврат вручную или скриптом `PUT` |
| Массовая ошибка | восстановление дампа БД, снятого перед запуском |

Особенности удаления: объекты, на которые уже есть ссылки (категория, по
которой созданы заявки; группа с назначенными заявками), удаляются в корзину
и остаются связанными — это корректное поведение, «чистого» отката здесь нет.
Отсюда вывод: **сначала dry-run и один объект, потом всё остальное**.

## 8. Отличия GLPI 11

| Тема | GLPI 10.x | GLPI 11.x |
|---|---|---|
| Точка входа | `/apirest.php` (API v1) | сохранена (legacy API, «мягко не рекомендуется», удалять не планируют); добавлена высокоуровневая `/api.php/v2/` |
| Аутентификация | `App-Token` + `Session-Token`, `initSession` по логину/паролю или `user_token` | v2 — OAuth2 (grant `password` для скриптов, `authorization_code` для интерактивных приложений) |
| Маршрутизация версий | — | `/api.php/v1/...` перенаправляется в legacy, `v2` и выше — в новую |
| Охват объектов | любой объект GLPI напрямую по itemtype | v2 работает с «схемами» (более удобно, но покрытие отличается от legacy) |
| Настройки API | Настройка → Общие → API, клиенты API | добавляется управление OAuth-клиентами |

Для Релиза 1 на GLPI 10.x всё написанное применимо без изменений. Если
инстанс окажется 11.x, скрипты на `apirest.php` продолжат работать; переход
на v2 — отдельная задача следующей волны.

Отдельно: в свежих патч-версиях 10.0.x и 11.0.x ужесточалось поведение API
(состав обязательных заголовков и параметров). Перед массовым запуском
скриптов стоит зафиксировать точную версию инстанса (нижний колонтитул
интерфейса или `php bin/console system:status`) и прогнать смоук-тест из
раздела 3 именно на ней.

## 9. Секреты, которые нужно завести

| Плейсхолдер | Что это | Минимальные права | Где используется |
|---|---|---|---|
| `<APP_TOKEN>` (`$GLPI_APP_TOKEN`) | токен клиента API «Release1 automation» | клиент ограничен одним IP `<AUTOMATION_IP>`, журналирование включено, деактивируется после работ | заголовок `App-Token` |
| `<GLPI_LOGIN>` / `<GLPI_PASSWORD>` | учётная запись автоматизации (`svc.api`) | профиль `Super-Admin` **на время работ Релиза 1**, с датой окончания действия; после — понижение до рабочего профиля или деактивация | `initSession` |
| `<AUTOMATION_IP>` | адрес рабочей станции администратора (не секрет) | — | фильтр доступа клиента API |

Зафиксировать письменно:

- кто из администраторов запускал скрипты и в какой период действовал
  `Super-Admin` у `svc.api`;
- дата отключения «Входа с учётными данными» после завершения работ;
- где хранится журнал операций (раздел 6) и дамп БД, снятый перед запуском.
