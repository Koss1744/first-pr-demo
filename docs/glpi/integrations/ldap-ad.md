# Подключение Active Directory (LDAP)

**Статус:** подготовлено к выполнению. Прямого доступа к инстансу
https://sd.hofi.su и к домену заказчика у автора документа нет.

**Релиз:** 1. AD — основной источник учётных записей (100–500 пользователей).
Локальные учётки GLPI сохраняются для подрядчиков и сервисных пользователей.

**Версия:** GLPI 10.x. Отличия 11.x — в отдельном разделе.

**Зависимость:** почтовый канал ([`mail-collector.md`](mail-collector.md))
определяет заявителя по адресу `From`. Значит адреса пользователей должны
быть в GLPI **до** объявления адреса поддержки. AD-синхронизация — это
поставщик адресов, её разумно включить первой или одновременно.

## 1. Параметры, которые должен предоставить заказчик

| Параметр | Плейсхолдер | Комментарий |
|---|---|---|
| Контроллер домена (основной) | `<LDAP_HOST>` | FQDN, не IP: нужен для LDAPS и Kerberos-независимой проверки сертификата |
| Контроллер домена (резервный) | `<LDAP_HOST_REPLICA>` | заводится в GLPI как «реплика» каталога |
| Порт | `<LDAP_PORT>` | 389 (+STARTTLS) или 636 (LDAPS) |
| Шифрование | `<LDAP_ENCRYPTION>` | LDAPS:636 — предпочтительно; STARTTLS на 389 — допустимо; без шифрования — недопустимо, пароли пользователей идут открытым текстом |
| Корневой DN поиска | `<LDAP_BASE_DN>` | например `OU=Users,OU=HOFI,DC=hofi,DC=local` — не `DC=hofi,DC=local` целиком |
| DN сервисной учётки | `<LDAP_BIND_DN>` | `CN=svc-glpi,OU=Service,DC=hofi,DC=local` |
| Пароль сервисной учётки | `<LDAP_BIND_PASSWORD>` | секрет, см. раздел 12 |
| Суффикс домена (UPN) | `<AD_DOMAIN>` | `hofi.su` / `hofi.local` |
| OU с обычными пользователями | `<OU_USERS>` | какие OU **не** импортировать (служебные, тестовые, ящики-ресурсы) |
| Группы для прав в GLPI | `<AD_GROUP_*>` | см. таблицу раздела 7 |
| Корневой сертификат CA | `<LDAP_CA_CERT>` | если LDAPS с внутренним CA — нужен на сервере GLPI |

Проверка до настройки в GLPI — [`checks.md`](checks.md), раздел LDAP.

## 2. Сервисная учётная запись AD

Требования (формулировка для администратора домена):

- отдельная учётка, например `svc-glpi`, **только для чтения каталога**;
- членство: `Domain Users` и не более. **Не** `Domain Admins`, **не**
  `Account Operators`;
- пароль длинный, не истекает (или регламент смены с обязательным
  обновлением в GLPI: при смене пароля молча ломается вход всех
  AD-пользователей);
- «Запретить интерактивный вход» (Log On To — ограничить, либо политикой
  Deny log on locally / Deny log on through RDS);
- учётка не входит в группы, дающие права в GLPI (иначе правила прав
  применятся к ней самой);
- зафиксировать владельца учётки и срок ревизии.

Чтения хватает: GLPI ничего не пишет в AD. Любой запрос «нужны права на
запись» — повод проверить, не пытаются ли ей же решать задачи другой системы.

## 3. Создание каталога в GLPI

Путь: **Настройка → Аутентификация → Каталоги LDAP → «+»**.

Использовать кнопку предустановки **Active Directory** — она проставляет
корректные значения. Ниже — что именно она ставит и что нужно поправить.

| Поле | Значение из предустановки AD | Значение для HOFI |
|---|---|---|
| Название | — | `AD hofi` |
| Сервер по умолчанию | — | Да |
| Активен | — | Да (после проверки) |
| Сервер | — | `<LDAP_HOST>` |
| Порт | 389 | `<LDAP_PORT>` (636 при LDAPS) |
| Использовать TLS | нет | Да при STARTTLS на 389; при LDAPS 636 — нет (шифрование даёт схема `ldaps://`) |
| BaseDN | — | `<LDAP_BASE_DN>` |
| RootDN (учётка для чтения) | — | `<LDAP_BIND_DN>` |
| Пароль | — | `<LDAP_BIND_PASSWORD>` |
| Фильтр соединения (`condition`) | `(&(objectClass=user)(objectCategory=person)(!(userAccountControl:1.2.840.113556.1.4.803:=2)))` | см. раздел 4 |
| Поле логина (`login_field`) | `samaccountname` | оставить |
| Поле синхронизации (`sync_field`) | `objectguid` | **оставить обязательно**, см. ниже |
| Использовать DN в поиске (`use_dn`) | 1 | оставить |
| Поддержка постраничного поиска | 1, размер 1000 | оставить (иначе AD обрежет выдачу на 1000 записей) |
| Таймаут | 0 | поставить 10 с, чтобы недоступный DC не вешал вход в GLPI |

**Поле синхронизации `objectGUID` — принципиально.** Оно позволяет GLPI
опознать пользователя после переименования (смена фамилии → смена
`sAMAccountName`). Без него переименованный сотрудник превращается в нового
пользователя, а старый помечается как удалённый из AD, и вся история заявок
остаётся на «мёртвой» учётке. Менять это поле после первой синхронизации
GLPI не даёт — значит решить надо до импорта.

Реплика: вкладка «Реплики LDAP» на созданном каталоге → добавить
`<LDAP_HOST_REPLICA>`. Реплики используются для чтения при недоступности
основного сервера.

## 4. Фильтр импорта пользователей

Требование заказчика: импортировать только активных, не заблокированных, с
почтой.

```
(&(objectCategory=person)
  (objectClass=user)
  (!(userAccountControl:1.2.840.113556.1.4.803:=2))
  (mail=*)
  (sAMAccountName=*)
)
```

Записывается в поле «Фильтр соединения» одной строкой (без переносов):

```
(&(objectCategory=person)(objectClass=user)(!(userAccountControl:1.2.840.113556.1.4.803:=2))(mail=*)(sAMAccountName=*))
```

Разбор:

| Условие | Что делает |
|---|---|
| `objectCategory=person` + `objectClass=user` | только пользователи; отсекает компьютеры и контакты |
| `!(userAccountControl:1.2.840.113556.1.4.803:=2)` | побитовая проверка флага `ACCOUNTDISABLE` — исключает **отключённые** учётки |
| `mail=*` | только с заполненным почтовым адресом |
| `sAMAccountName=*` | страховка от объектов без логина |

Дополнительные варианты (согласовать с заказчиком):

| Задача | Добавка к фильтру |
|---|---|
| Исключить служебные учётки по префиксу | `(!(sAMAccountName=svc-*))` |
| Исключить ящики-ресурсы/переговорки | `(!(msExchRecipientTypeDetails=16))` либо отдельной OU в BaseDN |
| Только сотрудники конкретной группы | `(memberOf=CN=<AD_GROUP_GLPI_USERS>,OU=Groups,DC=hofi,DC=local)` |
| С учётом вложенных групп | `(memberOf:1.2.840.113556.1.4.1941:=CN=<AD_GROUP>,...)` — «matching rule in chain», нагружает DC, применять точечно |

Два замечания, которые обычно всплывают позже:

1. **Ограничение области поиска лучше делать через BaseDN, а не фильтром.**
   `<LDAP_BASE_DN>` = OU с сотрудниками; служебные OU просто не попадают в
   область. Это быстрее для DC и понятнее при разборе.
2. **Этот же фильтр применяется при входе в GLPI.** Пользователь, не
   попадающий под фильтр (например, у него не заполнен `mail`), не сможет
   войти, даже если он уже импортирован. `lockoutTime` (временная
   блокировка после неверных паролей) в фильтре **не** используется:
   блокировка снимается сама, а исключённый пользователь пропадёт из
   синхронизации и будет обработан как «удалённый из AD».

Заблокированные (locked out) учётки не проходят аутентификацию на самом
DC — отдельный фильтр для них не нужен.

## 5. Маппинг атрибутов

Вкладка каталога — блок «Связь с каталогом LDAP».

| Поле GLPI | Атрибут AD | Комментарий |
|---|---|---|
| Логин (`login_field`) | `samaccountname` | ключ входа |
| Поле синхронизации (`sync_field`) | `objectguid` | неизменяемый идентификатор |
| Фамилия (`realname_field`) | `sn` | |
| Имя (`firstname_field`) | `givenname` | |
| Email 1 (`email1_field`) | `mail` | **критично для почтового канала** |
| Email 2–4 | `proxyaddresses` не использовать | дополнительные адреса заводить точечно |
| Телефон (`phone_field`) | `telephonenumber` | |
| Телефон 2 (`phone2_field`) | `othertelephone` | |
| Мобильный (`mobile_field`) | `mobile` | |
| Должность (`title_field`) | `title` | справочник «Звания/должности» пополняется автоматически |
| Категория пользователя (`category_field`) | `department` | так подразделение из AD попадает в GLPI (справочник «Категории пользователей») |
| Административный номер (`registration_number_field`) | `employeenumber` | если ведётся в AD |
| Расположение (`location_field`) | `physicaldeliveryofficename` | можно выражением: `%{l} > %{physicaldeliveryofficename}` |
| Ответственный (`responsible_field`) | `manager` | GLPI подставит руководителя, если он тоже импортирован |
| Комментарии (`comment_field`) | `info` | |
| Язык (`language_field`) | пусто | оставить пустым: язык интерфейса задаётся в GLPI |
| Изображение (`picture_field`) | `thumbnailphoto` | опционально; раздувает БД, в Релизе 1 не включать |

Отдельно про «отдел»: у пользователя GLPI нет поля «подразделение» как
такового. Практика — маппинг `department` → «Категория пользователя»
(таблица выше) и/или организация групп GLPI по подразделениям. Если нужен
именно отдельный атрибут — это плагин Fields, за пределами Релиза 1.

Выражения: в полях маппинга допускается конструкция `%{attribute}`,
например `%{givenname} %{sn}` или `%{city} > %{roomnumber}`.

## 6. Первичный импорт и группы

### 6.1. Импорт пользователей

Путь: **Администрирование → Пользователи → Связь с каталогом LDAP →
Импорт новых пользователей** (или «Синхронизация уже импортированных»).

Порядок:

1. Сначала «Проверить подключение» на форме каталога.
2. Импорт **на тестовой выборке**: во время импорта доступен фильтр —
   импортировать сначала 5–10 сотрудников ИТ, проверить маппинг полей у
   импортированных.
3. Убедиться, что заполнены: логин, ФИО, email, сущность, профиль.
4. Только потом — массовый импорт.

Ожидаемый объём: 100–500 записей, импорт занимает минуты. Если импорт
обрывается на 1000 записей — не включена поддержка постраничного поиска
(раздел 3).

### 6.2. Импорт групп

Путь: **Администрирование → Группы → Связь с каталогом LDAP → Импорт
групп**.

| Параметр | Значение для AD |
|---|---|
| Атрибут групп пользователя (`group_field`) | `memberof` |
| Тип поиска групп (`group_search_type`) | «в пользователях» (GROUP_SEARCH_USER) — членство читается из атрибута пользователя |
| Фильтр групп (`group_condition`) | по умолчанию из предустановки AD; для выборочного импорта — `(&(objectClass=group)(cn=GLPI-*))` |

Рекомендация: импортировать не все группы домена, а выделенные под GLPI
(соглашение об именовании `GLPI-*` или отдельная OU). Импорт 800 групп
домена в GLPI превращает справочник групп в свалку и мешает назначению
заявок на группы поддержки.

Группы GLPI нужны для двух разных задач — не путать:

- **группы поддержки** (кому назначают заявки) — создаются вручную по
  результатам работы аналитика, из AD не импортируются;
- **группы-зеркала AD** (подразделения, признак прав) — импортируются, на них
  опираются правила прав.

## 7. Правила назначения профилей и сущностей

Путь: **Администрирование → Правила → Правила назначения прав** (RuleRight).
Правила выполняются при каждом входе пользователя и при синхронизации.

Доступные критерии: тип аутентификации, каталог LDAP, почтовый сервер,
email, логин, группа GLPI, плюс **любой атрибут LDAP**, заведённый в
справочнике критериев.

Доступные действия (нужные в Релизе 1): сущность, профиль, «рекурсивный»,
сущность по DN/по тегу/по домену почты, группа по умолчанию, «не
импортировать пользователя».

### 7.1. Два способа матчинга по группам AD

**Способ А (рекомендуемый): через импортированные группы.**
AD-группы импортированы в GLPI (6.2) → критерий правила «Группа» →
выбирается группа из справочника. Понятно, не требует регулярных выражений,
видно в интерфейсе.

**Способ Б: по атрибуту `memberOf` напрямую.**
Требует подготовки: **Администрирование → Правила → Критерии LDAP** (словарь
`RuleRightParameter`) — добавить запись с названием `(LDAP) memberOf` и
значением `memberof`. После этого в правилах появляется критерий
`(LDAP) memberOf`, по нему матчатся DN групп регулярным выражением:

```
/CN=GLPI-Technicians,OU=Groups,DC=hofi,DC=local/i
```

По умолчанию в GLPI заведены критерии `(LDAP)Organization` (`o`),
`(LDAP)Common Name` (`cn`), `(LDAP)Department Number`, `(LDAP)Email`,
`(LDAP)User ID`, `(LDAP)Manager`, `(LDAP)DistinguishedName` и т.п., но
**`memberof` среди них нет** — его добавляют руками. Это и есть причина
самой частой жалобы «правила по группам AD не срабатывают».

### 7.2. Матрица правил (черновик, уточняется аналитиком)

Порядок правил важен: они выполняются сверху вниз, более частные — выше.

| № | Правило | Критерий | Действия |
|---|---|---|---|
| 1 | Администраторы GLPI | Группа = `<AD_GROUP_GLPI_ADMINS>` | Профиль `Admin`, Сущность «Корень», Рекурсивный: Да |
| 2 | Специалисты поддержки | Группа = `<AD_GROUP_GLPI_TECHNICIANS>` | Профиль `Technician`, Сущность «Корень», Рекурсивный: Да |
| 3 | Руководители (просмотр отчётов) | Группа = `<AD_GROUP_GLPI_SUPERVISORS>` | Профиль `Supervisor`, Сущность по подразделению |
| 4 | Все остальные сотрудники | Каталог LDAP = `AD hofi` | Профиль `Self-Service`, Сущность по умолчанию, Рекурсивный: Нет |

Правило 4 — «страховочное», всегда последнее и без «остановки обработки»
выше него. Без него импортированный пользователь попадает в GLPI без
профиля и получает при входе «Пользователю не разрешено подключаться к GLPI».

Назначение сущности, если в компании больше одной сущности:

| Подход | Действие правила | Когда применять |
|---|---|---|
| По DN пользователя | «Сущность на основе данных LDAP» + regex по OU | структура OU повторяет оргструктуру |
| По домену почты | «Сущность из почтового домена» | несколько юрлиц с разными доменами |
| Явно | «Сущность» = конкретная | 1–3 сущности, простая структура |

Для Релиза 1 при одной сущности всё упрощается: правила 1–4 с явной
корневой сущностью.

### 7.3. Динамические и ручные права

Права, выданные правилом, помечаются в GLPI как **динамические**. При
следующем входе/синхронизации GLPI пересчитывает их: если пользователь выбыл
из группы AD, динамический профиль снимается. Права, назначенные вручную на
карточке пользователя, — **ручные (не динамические)** и правилами не
трогаются.

Отсюда практическое правило проекта:

- права AD-пользователей выдаются **только правилами**, не руками;
- права локальных учёток (подрядчики, сервисные) выдаются **только руками**,
  чтобы их не снесло пересчётом (см. раздел 8.3).

## 8. Сосуществование AD-учёток и локальных учёток GLPI

Это тот раздел, из-за которого проекты внедрения теряют доступ в систему.

### 8.1. Порядок источников аутентификации

При входе GLPI пробует источники строго в таком порядке:

1. **Внешняя аутентификация** (SSO/CAS/заголовки веб-сервера), если включена;
2. **Локальная база GLPI** — пользователи с типом «Внутренняя база GLPI»
   (`authtype = 1`, `auths_id = 0`) и заданным паролем;
3. **Каталоги LDAP** — все активные каталоги, по очереди (или конкретный,
   если у пользователя уже зафиксирован `auths_id`);
4. **Почтовые серверы аутентификации** (IMAP-аутентификация), если заведены.

Практические следствия:

- **Включение LDAP не ломает локальные учётки**: они проверяются раньше.
  Локальный `glpi`/`admin` продолжает работать.
- При **совпадении логинов** (в AD есть `ivanov`, и в GLPI есть локальный
  `ivanov`) побеждает локальная учётка — пользователь AD войти не сможет,
  а «почему» будет неочевидно. Локальные логины должны иметь свою
  неконфликтующую схему именования, например `ext.ivanov`, `svc.backup`.
- У каждого пользователя в GLPI зафиксирован свой тип аутентификации: после
  первого успешного входа через AD у него `authtype = LDAP` и ссылка на
  каталог. Это поле нельзя «переключить» массово — перевод локальной учётки в
  AD делается удалением локальной и импортом из AD (история заявок при этом
  теряется, поэтому решается до старта).

### 8.2. Чек-лист «не сломать вход при включении LDAP»

Выполнять в этом порядке:

1. **Зафиксировать локального администратора.** Убедиться, что существует
   рабочая локальная учётка с профилем `Super-Admin`, тип «Внутренняя база
   GLPI», известный пароль, и она **не** совпадает по логину ни с одной
   учёткой AD. Проверить вход в приватном окне браузера **до** включения LDAP.
2. Каталог создаётся с «Активен: Нет», проверка подключения — кнопкой на форме.
3. Правила прав создаются **до** первого массового импорта (иначе 500
   пользователей импортируются без профилей, и придётся чинить массовыми
   действиями).
4. Импорт сначала на 5–10 тестовых пользователях.
5. Проверка входа тестового AD-пользователя в приватном окне (текущая
   сессия администратора при этом не теряется).
6. Массовый импорт.
7. Включить отображение выбора источника аутентификации на странице входа
   (Настройка → Аутентификация → Настройка аутентификации → «Показывать
   источник входа»): это даёт возможность явно войти «в локальную базу»,
   если LDAP недоступен.
8. Зафиксировать в `docs/glpi/config-log.md` дату включения и параметры.

### 8.3. Как правила прав влияют на локальные учётки

Правила назначения прав применяются **и при локальном входе** (тип
аутентификации «Внутренняя база GLPI»). Широкое правило вида «всем — профиль
Self-Service, сущность Корень» затронет и подрядчиков, и сервисные учётки.

Защита:

- у страховочного правила (7.2, № 4) выставлять критерий **«Каталог LDAP =
  AD hofi»**, а не «применять ко всем»;
- либо добавить критерий «Тип аутентификации = LDAP»;
- права локальных учёток назначать вручную (они не динамические и
  пересчётом не снимаются);
- локального `Super-Admin` вообще исключить из области действия правил
  (критерий «Логин ≠ ...» в первом правиле со «стоп обработки»).

### 8.4. Локальные учётки: для кого и как

| Категория | Пример логина | Профиль | Особенности |
|---|---|---|---|
| Подрядчик (внешний специалист) | `ext.ivanov` | `Technician` ограниченный / `Self-Service` | обязательно заполнить email — иначе не работает почтовый канал; срок действия учётки (поле «Действителен до») |
| Сервисная учётка для API | `svc.api` | выделенный профиль, минимальные права | см. [`api-enable.md`](api-enable.md) |
| Аварийный администратор | `local.admin` | `Super-Admin` | пароль в менеджере паролей, вход проверяется ежеквартально |

Для локальных учёток обязательно заполнять поле «Действителен до» там, где
известен срок договора: GLPI сам деактивирует учётку по истечении.

## 9. Уволенные сотрудники

Принцип: **деактивация, а не удаление**. Заявки, комментарии и история
уволенного должны остаться и должны быть доступны для отчётов.

Путь: **Настройка → Аутентификация → Настройка аутентификации** → «Действие
при удалении пользователя из каталога LDAP» (`user_deleted_ldap`).

| Вариант | Что делает | Оценка |
|---|---|---|
| Сохранить | ничего не делать | нет: уволенный сможет войти, если учётка в AD ещё активна |
| Поместить в корзину | удаление в корзину GLPI | нет: пользователь пропадает из списков и назначений |
| Снять динамические права и группы | остаётся активен, но без прав | частично: учётка формально активна |
| **Отключить** | `is_active = 0`, вход запрещён, данные на месте | **рекомендуется как минимум** |
| **Отключить + снять динамические права и группы** | то же + чистка прав и групп | **рекомендуется для HOFI** |
| Отключить + снять группы | то же без снятия прав | промежуточный вариант |

Рядом настраивается **«Действие при восстановлении пользователя в каталоге
LDAP»** (`user_restored_ldap`): «Ничего не делать» / «Восстановить из
корзины» / «Активировать». Для HOFI — «Активировать»: вернувшийся сотрудник
(или ошибочно отключённый) восстанавливается автоматически.

Как это срабатывает:

- при синхронизации: пользователь не найден по фильтру → применяется
  выбранное действие, у пользователя выставляется флаг «удалён из LDAP»;
- при попытке входа: пользователь не найден в каталоге → то же действие,
  вход запрещён.

Важно: **отключение учётки в AD** (что и делает кадровая процедура при
увольнении) выводит пользователя из-под фильтра раздела 4
(`!(userAccountControl...=2)`), и GLPI обработает его как удалённого. То есть
отдельная процедура для GLPI не нужна — достаточно штатного увольнения в AD.

Чего это **не** делает автоматически и что нужно регламентом:

1. **Открытые заявки уволенного** остаются назначенными на него. Перед
   увольнением заявки переназначаются (это пункт регламента увольнения,
   владелец — руководитель ИТ).
2. **Заявки, где уволенный — заявитель**, остаются: это корректно, история
   не переписывается.
3. **Локальные учётки подрядчиков** AD не отслеживает: по окончании договора
   их деактивируют вручную или по полю «Действителен до».

## 10. Регулярная синхронизация

В ядре GLPI 10 **нет автодействия для синхронизации LDAP** — это регулярная
причина удивления («включил каталог, а данные не обновляются»).
Синхронизация выполняется одним из способов:

| Способ | Когда применять |
|---|---|
| CLI-команда по расписанию (cron) | штатный продуктивный вариант |
| Массовое действие в интерфейсе (Администрирование → Пользователи → Связь с каталогом LDAP) | разовые операции, первичный импорт |
| При входе пользователя | данные конкретного пользователя обновляются автоматически |

### 10.1. CLI-команда

```bash
# полная синхронизация: создать новых + обновить существующих + обработать удалённых
php /var/www/glpi/bin/console ldap:synchronize_users --ldap-server-id=<LDAP_SERVER_ID> --no-interaction

# только обновление существующих (не создаёт новых, не трогает удалённых)
php /var/www/glpi/bin/console ldap:synchronize_users -u --ldap-server-id=<LDAP_SERVER_ID>

# только импорт новых
php /var/www/glpi/bin/console ldap:synchronize_users -c --ldap-server-id=<LDAP_SERVER_ID>

# инкрементально: только изменённые в AD за последние сутки (по modifyTimestamp)
php /var/www/glpi/bin/console ldap:synchronize_users --begin-date="-1 day" --ldap-server-id=<LDAP_SERVER_ID>
```

Полезные опции: `--ldap-filter` (переопределить фильтр разово),
`--deleted-user-strategy` / `--restored-user-strategy` (переопределить
действие для удалённых/восстановленных), `--begin-date` / `--end-date`.
Алиас команды — `ldap:sync`.

Команда запускается **от пользователя веб-сервера** (иначе созданные файлы
логов получат неверного владельца):

```cron
# инкрементальная синхронизация каждый час в рабочее время
15 7-20 * * 1-5 /usr/bin/php /var/www/glpi/bin/console ldap:synchronize_users --ldap-server-id=<LDAP_SERVER_ID> --begin-date="-2 hours" --no-interaction >> /var/log/glpi/ldap-sync.log 2>&1

# полная сверка ночью (в т.ч. обработка уволенных)
30 2 * * * /usr/bin/php /var/www/glpi/bin/console ldap:synchronize_users --ldap-server-id=<LDAP_SERVER_ID> --no-interaction >> /var/log/glpi/ldap-sync.log 2>&1
```

Обоснование расписания: почасовая инкрементальная синхронизация даёт быстрое
появление новых сотрудников (важно для почтового канала: без email в GLPI
письмо новичка будет отклонено), ночная полная — корректно обрабатывает
уволенных и не нагружает DC днём.

Для 100–500 пользователей полная синхронизация занимает единицы минут.

### 10.2. Что проверять после каждого изменения расписания

- `/var/log/glpi/ldap-sync.log` — счётчики созданных/обновлённых/удалённых;
- Администрирование → Пользователи → фильтр «Активен = Нет» — не выросло ли
  число деактивированных скачком (признак сломанного фильтра: см. раздел 11);
- журнал GLPI `files/_log/`.

## 11. Типовые ошибки

| Симптом | Причина | Проверка / решение |
|---|---|---|
| «Не удалось подключиться к каталогу LDAP» | закрыт порт, неверный FQDN, недоступен DC | `checks.md` → LDAP: `nc`/`openssl s_client`, `ldapsearch` |
| Подключение проходит, пользователей 0 | неверный BaseDN или слишком узкий фильтр | тот же `ldapsearch` с тем же BaseDN и фильтром: если он ничего не возвращает — дело не в GLPI |
| Импортируется ровно 1000 пользователей | не включена поддержка постраничного поиска | каталог → «Поддержка постраничного поиска» = Да, размер 1000 |
| `Invalid credentials (49)` | неверный `<LDAP_BIND_DN>` или пароль; пароль истёк | проверить `ldapwhoami`; частая причина — политика смены пароля сервисной учётки |
| Вход работал и внезапно перестал у всех | сменился пароль сервисной учётки; DC выведен из эксплуатации; включён LDAP channel binding/signing без LDAPS | обновить пароль в каталоге; добавить реплику; перейти на LDAPS 636 |
| LDAPS не соединяется, а 389 работает | на сервере GLPI нет корневого сертификата внутреннего CA | положить `<LDAP_CA_CERT>` в системное хранилище доверия, проверить `openssl s_client -connect <LDAP_HOST>:636` |
| Пользователи импортированы без email | атрибут `mail` в AD не заполнен либо неверный маппинг | выборка `ldapsearch ... mail`; заполнение в AD — задача заказчика |
| Правила по группам AD не срабатывают | группы не импортированы **или** не заведён критерий `(LDAP) memberOf` | раздел 7.1 |
| Пользователь входит, но видит «Пользователю не разрешено подключаться» | не назначен профиль: нет страховочного правила или оно выше частных | раздел 7.2 |
| После включения LDAP пропали права у части пользователей | сработал пересчёт динамических прав; ручные права перезаписаны правилами | раздел 7.3, 8.3 |
| После переименования сотрудника появился дубль | не задано поле синхронизации `objectguid` | раздел 3; исправляется только пересозданием связки, поэтому решается до импорта |
| Массово деактивировались пользователи | изменился фильтр/BaseDN → все «не найдены в AD» | откатить фильтр, запустить синхронизацию повторно, восстановление через `user_restored_ldap` = «Активировать» |
| Вход в GLPI стал медленным | недоступная реплика, большой таймаут, нет постраничного поиска | таймаут 10 с, проверить доступность всех DC из списка реплик |
| Уволенный продолжает входить | учётка в AD не отключена, а только «перемещена в OU Уволенные» вне BaseDN | если OU вне BaseDN, GLPI считает пользователя удалённым и применит `user_deleted_ldap` — проверить, что значение настроено (раздел 9) |

Порядок диагностики: **сеть/порт → учётные данные → права сервисной учётки →
конфигурация GLPI → логи (`files/_log/`) → расписание синхронизации**.

## 12. Откат

1. **Немедленно:** Настройка → Аутентификация → Каталоги LDAP → каталог →
   «Активен: Нет». AD-пользователи перестают входить, локальные учётки
   продолжают работать (порядок источников, раздел 8.1). Данные
   импортированных пользователей остаются.
2. **Остановить синхронизацию:** закомментировать строки cron из 10.1.
3. **Откатить правила прав:** правила деактивируются («Активно: Нет») по
   одному, начиная с последнего добавленного. Права пересчитаются при
   следующем входе пользователя.
4. **Массовая деактивация «по ошибке»:** Администрирование → Пользователи →
   фильтр по дате изменения → массовое действие «Активен = Да». Если было
   выбрано действие «Поместить в корзину» — массовое восстановление из
   корзины.
5. **Полное удаление каталога** — крайняя мера: вместе с ним теряется
   привязка пользователей к источнику, при повторном включении они будут
   импортированы заново. Перед этим — dump БД.
6. Дамп БД GLPI снимается **до** первого массового импорта и **до** каждого
   изменения фильтра. Это единственный надёжный откат массовых изменений
   пользователей.

## 13. Отличия GLPI 11

| Тема | GLPI 10.x | GLPI 11.x |
|---|---|---|
| Команда синхронизации | `bin/console ldap:synchronize_users` | имя команды сохранено |

## 14. Секреты, которые нужно завести

| Плейсхолдер | Что это | Минимальные права | Где используется |
|---|---|---|---|
| `<LDAP_BIND_PASSWORD>` | пароль сервисной учётки `<LDAP_BIND_DN>` | членство только в `Domain Users`; чтение атрибутов пользователей и групп в `<LDAP_BASE_DN>`; запрет интерактивного входа; без прав записи в AD | поле «Пароль» каталога LDAP в GLPI |
| `<LDAP_CA_CERT>` | корневой сертификат внутреннего CA (не секрет, но нужен) | — | хранилище доверенных сертификатов на сервере GLPI |
| пароль локального `Super-Admin` | аварийный вход | `Super-Admin` в GLPI | менеджер паролей компании; проверка входа ежеквартально |

Зафиксировать письменно:

- владелец сервисной учётки `<LDAP_BIND_DN>` и регламент смены пароля
  (со шагом «обновить пароль в GLPI»);
- кто в компании отвечает за состав групп `<AD_GROUP_GLPI_*>` — фактически
  это владелец прав доступа в GLPI;
- решение заказчика по варианту `user_deleted_ldap` (раздел 9) — оно
  определяет, что происходит с уволенными.
