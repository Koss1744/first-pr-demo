# Почтовый канал приёма заявок (IMAP-коллектор + SMTP)

**Статус:** подготовлено к выполнению. Прямого доступа к инстансу
https://sd.hofi.su и к почтовому контуру у автора документа нет — все шаги
выполняет администратор на месте.

**Релиз:** 1 (критичный путь). Цель — перевести поток заявок из мессенджеров
и личных ящиков сотрудников ИТ в один ящик поддержки, из которого GLPI
создаёт заявки.

**Версия:** GLPI 10.x. Отличия 11.x — в разделе «Отличия GLPI 11».

---

## 1. Как это работает

```
Пользователь ─письмо──► support@<DOMAIN> ──IMAP──► GLPI (автодействие mailgate)
                                                        │
                                          новая заявка ──┤
                                          или фолоуап к существующей
                                                        │
GLPI ──SMTP──► уведомление пользователю (From: support@<DOMAIN>,
               тема «[HOFI #0000123] ...», Message-Id GLPI)
                                                        │
Пользователь «Ответить» ──► support@<DOMAIN> ──► фолоуап в заявку #123
```

Два независимых канала, которые настраиваются отдельно и ломаются отдельно:

| Канал | Что делает | Где настраивается |
|---|---|---|
| IMAP (входящий) | забирает письма из ящика, создаёт заявки/фолоуапы | Настройка → Получатели (Setup → Receivers) |
| SMTP (исходящий) | отправляет уведомления | Настройка → Уведомления → Настройка уведомлений по почте |

Важно: обратная привязка ответа к заявке работает только если исходящие
уведомления реально уходят. Сначала настраивается SMTP, потом IMAP.

## 2. Параметры, которые должен предоставить заказчик

Без этих данных настройка не начинается. Пароли передаются не через git и не
через переписку в мессенджере, а через согласованный канал (менеджер паролей
/ защищённая заметка).

### 2.1. Ящик поддержки

| Параметр | Плейсхолдер | Пример/комментарий |
|---|---|---|
| Адрес ящика поддержки | `<SUPPORT_MAILBOX>` | `support@hofi.su`. Отдельный ящик, **не личный ящик сотрудника** |
| Отображаемое имя | `<SUPPORT_DISPLAY_NAME>` | `Служба поддержки HOFI` |
| Тип почтовой системы | `<MAIL_PLATFORM>` | MS Exchange on-prem / Microsoft 365 / Yandex 360 / MDaemon / прочее |
| Кто владелец ящика | — | ФИО + подразделение, кто продлевает пароль |

### 2.2. IMAP (приём)

| Параметр | Плейсхолдер | Комментарий |
|---|---|---|
| IMAP-сервер | `<IMAP_HOST>` | FQDN, не IP (нужен для проверки сертификата) |
| Порт | `<IMAP_PORT>` | 993 (SSL) или 143 (STARTTLS). 993 предпочтителен |
| Шифрование | `<IMAP_ENCRYPTION>` | SSL / TLS / нет (последнее — недопустимо для продуктива) |
| Логин | `<IMAP_LOGIN>` | Может отличаться от адреса: `DOMAIN\support` или `support@hofi.su` |
| Пароль | `<IMAP_PASSWORD>` | Секрет, см. раздел 13 |
| Разрешён ли Basic Auth | — | Для Microsoft 365 Basic Auth для IMAP отключён → нужен OAuth (см. 6.4) |
| Папка входящих | `<IMAP_INBOX>` | Обычно `INBOX` |
| Папка «принятые» | `<IMAP_FOLDER_ACCEPTED>` | Предлагается `GLPI/accepted` |
| Папка «отклонённые» | `<IMAP_FOLDER_REFUSED>` | Предлагается `GLPI/refused` |
| Квота ящика | — | Нужна, чтобы оценить срок хранения архивных папок |

### 2.3. SMTP (уведомления)

| Параметр | Плейсхолдер | Комментарий |
|---|---|---|
| SMTP-сервер | `<SMTP_HOST>` | |
| Порт | `<SMTP_PORT>` | 587 (STARTTLS) / 465 (SSL) / 25 (только внутренний релей) |
| Шифрование | `<SMTP_ENCRYPTION>` | SMTP+TLS / SMTP+SSL / без шифрования (внутренний релей) |
| Логин | `<SMTP_LOGIN>` | Может быть пустым для анонимного внутреннего релея |
| Пароль | `<SMTP_PASSWORD>` | Секрет |
| Разрешена ли отправка от имени `<SUPPORT_MAILBOX>` | — | Обязательно: GLPI шлёт письма с этого адреса |
| Разрешён ли релей с IP сервера GLPI | `<GLPI_SERVER_IP>` | Для анонимного релея — единственная защита |

### 2.4. Сетевой доступ

| Откуда | Куда | Порт | Зачем |
|---|---|---|---|
| Сервер GLPI | `<IMAP_HOST>` | `<IMAP_PORT>` | забор писем |
| Сервер GLPI | `<SMTP_HOST>` | `<SMTP_PORT>` | уведомления |

Проверка доступа — до создания коллектора, команды в
[`checks.md`](checks.md).

## 3. Требования к ящику поддержки (выполняет почтовый администратор)

Эти пункты важнее, чем сама конфигурация GLPI: большинство инцидентов
почтового канала — это неправильно настроенный ящик, а не GLPI.

1. **Ящик отдельный.** Не переиспользовать личный ящик сотрудника ИТ и не
   переиспользовать ящик, на который уже настроены рассылки. GLPI забирает
   и (по умолчанию) удаляет/перемещает письма — личную переписку это уничтожит.
2. **Автоответ на ящике выключен.** Ящик поддержки не должен отвечать
   «Здравствуйте, ваше обращение принято» средствами почтовой системы — это
   делает GLPI. Два автоответчика = петля.
3. **Правила пересылки/перенаправления выключены.** Иначе письмо будет
   обработано дважды или уйдёт в чужой ящик.
4. **Ящик не подписан на рассылки и не входит в списки рассылки.** Любая
   рассылка станет потоком заявок.
5. **Ящик исключён из всех «уведомлений мониторинга»** до отдельного решения:
   мониторинг шлёт сотни писем и требует собственных правил.
6. **Созданы папки** `<IMAP_FOLDER_ACCEPTED>` и `<IMAP_FOLDER_REFUSED>`
   (обычные IMAP-папки). Для POP папки недоступны — ещё одна причина
   использовать IMAP.
7. **Квота и регламент очистки архивных папок** согласованы (иначе через
   полгода ящик переполнится и коллектор встанет).
8. **Политика паролей:** пароль сервисного ящика не истекает раз в 30 дней
   либо процесс смены пароля включает обновление в GLPI. Иначе коллектор
   «внезапно» перестаёт работать.
9. **IMAP включён для ящика.** В Microsoft 365 / Exchange протокол IMAP
   может быть отключён политикой на уровне организации или ящика.

## 4. Порядок внедрения (чек-лист)

Порядок не произвольный: каждый шаг отсекает класс проблем.

1. Заказчик предоставил параметры раздела 2, ящик подготовлен по разделу 3.
2. Проверка сети и учётных данных **вне GLPI** — `checks.md`, разделы IMAP и SMTP.
3. Настройка SMTP-уведомлений в GLPI (раздел 5), тестовое письмо администратору.
4. Проверка автодействия `queuednotification` (уведомления ставятся в очередь
   и отправляются автодействием, а не мгновенно).
5. Создание коллектора **в неактивном состоянии** (`Активен: Нет`) (раздел 6).
6. **Создание правил защиты от автоответов (раздел 8) — до первой активации.**
7. Ручной прогон: вкладка «Получить письма» коллектора на тестовых письмах.
8. Активация коллектора, автодействие `mailgate` в режиме CLI (раздел 7).
9. Приёмочные тесты (раздел 10).
10. Наблюдение 3 рабочих дня: счётчик «Отклонённые письма», объём заявок,
    журнал `files/_log/mailgate.log`.
11. Только после этого — объявление адреса `<SUPPORT_MAILBOX>` пользователям.

Шаг 6 не переставлять и не пропускать. Обоснование — раздел 8.3.

## 5. SMTP: уведомления

Путь: **Настройка → Уведомления → Настройка уведомлений по почте**
(предварительно: **Настройка → Уведомления → Уведомления** — включить
«Использовать уведомления по email»).

| Поле (интерфейс) | Ключ конфигурации | Рекомендуемое значение |
|---|---|---|
| Email администратора | `admin_email` | `<IT_ADMIN_EMAIL>` (ящик группы ИТ, не личный) |
| Имя администратора | `admin_email_name` | `HOFI Service Desk` |
| Email отправителя | `from_email` | `<SUPPORT_MAILBOX>` |
| Имя отправителя | `from_email_name` | `<SUPPORT_DISPLAY_NAME>` |
| Адрес Reply-To | `replyto_email` | `<SUPPORT_MAILBOX>` |
| Имя Reply-To | `replyto_email_name` | `<SUPPORT_DISPLAY_NAME>` |
| Адрес No-Reply | `noreply_email` | оставить пустым в Релизе 1 |
| Добавлять документы в уведомления | `attach_ticket_documents_to_mail` | Нет (на старте; вложения раздувают письма) |
| Подпись email | `mailing_signature` | подпись службы поддержки |
| Способ отправки | `smtp_mode` | SMTP+TLS (`MAIL_SMTPTLS`) или SMTP+SSL |
| Проверять сертификат | `smtp_check_certificate` | Да |
| SMTP-сервер | `smtp_host` | `<SMTP_HOST>` |
| Порт | `smtp_port` | `<SMTP_PORT>` |
| Логин SMTP | `smtp_username` | `<SMTP_LOGIN>` |
| Пароль SMTP | `smtp_passwd` | `<SMTP_PASSWORD>` |
| Макс. число попыток доставки | `smtp_max_retries` | 5 |
| Повторять через (мин) | `smtp_retry_time` | 5 |

Ключевое требование Релиза 1: **`from_email` = `<SUPPORT_MAILBOX>`**. Тогда
«Ответить» в почтовом клиенте пользователя ведёт обратно в GLPI, а не в
никуда. Если в компании принято слать уведомления с `noreply@`, почтовый
канал становится односторонним и ответ пользователя теряется — это прямо
противоречит цели релиза.

После сохранения — кнопка **«Отправить тестовое письмо администратору»**.
Письмо не приходит мгновенно: оно попадает в очередь (`glpi_queuednotifications`)
и отправляется автодействием `queuednotification` (по умолчанию раз в 60 с,
до 50 писем за проход). Если тест «прошёл», но письма нет — смотреть
Настройка → Автодействия → `queuednotification` и Настройка → Уведомления →
«Очередь уведомлений».

### 5.1. Префикс темы — основа привязки ответов

Путь: **Администрирование → Сущности → <корневая сущность> → вкладка
«Уведомления» → «Префикс для уведомлений»** (поле `notification_subject_tag`).

Для заявок GLPI формирует тему уведомления как `[<ПРЕФИКС> #0000123] ...`
(семизначный номер). Если префикс пуст, используется `GLPI`.

Рекомендация: `HOFI`. Тогда тема выглядит как
`[HOFI #0000123] Новая заявка — не работает принтер`.

**Не удалять номер из темы шаблонов уведомлений.** Тег `[... #123]` — это
резервный (и в реальности основной для веб-почты) механизм привязки ответа
к заявке, см. раздел 9.

## 6. IMAP-коллектор

Путь: **Настройка → Получатели** (Setup → Receivers) → «+».

Предусловие: на сервере должен быть доступен ключ шифрования GLPI
(`config/glpi.key`) — пароль ящика хранится зашифрованным. Если ключ
недоступен веб-серверу, форма коллектора не откроется вовсе.

### 6.1. Поля формы

| Поле | Значение для HOFI | Комментарий |
|---|---|---|
| Название | `<SUPPORT_MAILBOX>` | **Если название — валидный email, GLPI автоматически считает его адресом в чёрном списке отправителей.** Это бесплатная защита от петли «GLPI пишет сам себе»: указывайте здесь именно адрес ящика |
| Активен | сначала **Нет**, после настройки правил — **Да** | |
| Сервер | `<IMAP_HOST>` | |
| Тип соединения | IMAP | POP не использовать: нет папок, нет «только непрочитанные» |
| SSL | Да (для порта 993) | |
| TLS | Нет (при SSL/993) | Для 143 + STARTTLS: TLS = Да, SSL = Нет |
| Проверять сертификат | Да | `novalidate-cert` — только как временная мера диагностики |
| Порт | `<IMAP_PORT>` | |
| Папка | `<IMAP_INBOX>` (INBOX) | |
| Логин | `<IMAP_LOGIN>` | |
| Пароль | `<IMAP_PASSWORD>` | |
| Папка архива принятых писем | `<IMAP_FOLDER_ACCEPTED>` | Обязательно заполнить: иначе письма удаляются безвозвратно |
| Папка архива отклонённых писем | `<IMAP_FOLDER_REFUSED>` | Обязательно: это ваш журнал разбора «почему заявка не создалась» |
| Макс. размер файла, импортируемого получателем | 5–10 МБ | 0 = вложения не импортировать вообще |
| Использовать дату письма вместо даты сбора | Да | Дата заявки = дата письма пользователя |
| Использовать Reply-To как заявителя | Нет | «Да» нужно только если письма приходят через внешний шлюз/форму, подставляющую Reply-To |
| Добавлять пользователей в копии как наблюдателей | Да | Коллеги в копии видят заявку |
| Собирать только непрочитанные письма | Да | Защита на этапе обкатки: уже прочитанное вручную не превратится в заявки |
| Комментарии | ссылка на этот документ | |

Внутри GLPI параметры соединения хранятся строкой вида
`{<IMAP_HOST>:993/imap/ssl}INBOX`; при STARTTLS — `/imap/tls`, при
отключённой проверке сертификата добавляется `/novalidate-cert`.
Руками эту строку править не нужно, но она видна в отладке и в БД.

### 6.2. Кто станет заявителем

GLPI ищет пользователя по адресу из заголовка `From` (или `Reply-To`, если
включено). Дальше возможны варианты:

| Ситуация | Поведение | Что настроить |
|---|---|---|
| Адрес найден у пользователя GLPI | Заявка от его имени | Требует, чтобы email пользователя был в GLPI — его даёт синхронизация AD ([`ldap-ad.md`](ldap-ad.md)) |
| Адрес не найден, анонимные заявки разрешены | Заявка создаётся, заявитель — «внешний» адрес | Настройка → Общие → Помощь: «Разрешить анонимные заявки» (`use_anonymous_helpdesk`) |
| Адрес не найден, анонимные заявки запрещены | Письмо отклонено, попадает в «Отклонённые письма» | |

Рекомендация для Релиза 1: анонимные заявки **выключены**, но AD
синхронизирован заранее — иначе половина писем будет отклонена. Подрядчикам
и внешним контактам заводятся локальные учётки с email (см. `ldap-ad.md`,
раздел о локальных учётках).

### 6.3. Вложения

- Импортируются, если `Макс. размер файла > 0`.
- Каталог `files/_tmp` (GLPI_TMP_DIR) должен быть доступен на запись
  пользователю веб-сервера, иначе в `files/_log/mailgate.log` появится
  «... is not writable», а письмо придёт без вложений.
- **Расширение файла должно быть в справочнике «Типы документов»**
  (Настройка → Справочники → Типы документов) и тип должен быть активен.
  Самая частая жалоба «вложения из почты не приходят» — это отсутствующие
  типы (`.msg`, `.heic`, `.7z`, `.log`).
- Ограничение на размер также накладывают `upload_max_filesize` и
  `post_max_size` в PHP — коллектор пишет файл через ту же подсистему.
- Встроенные в письмо картинки (подписи, скриншоты из буфера) импортируются
  как документы и засоряют заявки: это ожидаемое поведение, чистится
  регламентом, а не настройкой.

### 6.4. Microsoft 365 / Exchange Online

Basic Auth для IMAP в Microsoft 365 отключён. Варианты:

1. **OAuth**: GLPI 10.0.6+ поддерживает OAuth для SMTP в ядре
   (режим SMTP+OAUTH); для IMAP-коллектора используется плагин
   `oauthimap`. Требуется регистрация приложения в Entra ID, права
   `IMAP.AccessAsUser.All` / `SMTP.Send`, согласие администратора.
2. **Внутренний релей/ящик на своей почтовой системе**: ящик поддержки
   размещается на on-prem системе, где Basic Auth доступен.

Выбор фиксируется заказчиком до настройки: он меняет состав секретов
(вместо `<IMAP_PASSWORD>` появляются `<OAUTH_CLIENT_ID>` /
`<OAUTH_CLIENT_SECRET>` / `<OAUTH_TENANT_ID>`).

## 7. Автодействия

Путь: **Настройка → Автодействия**.

| Автодействие | Что делает | Значение по умолчанию | Рекомендация для HOFI |
|---|---|---|---|
| `mailgate` | забирает письма из всех активных коллекторов | частота 600 с, параметр 10 писем за проход | частота 300 с, параметр 50 |
| `mailgateerror` | шлёт администратору уведомление о коллекторах в ошибке | раз в сутки | оставить, убедиться что `admin_email` верный |
| `queuednotification` | отправляет письма из очереди | 60 с, 50 писем | оставить |
| `queuednotificationclean` | чистит очередь | раз в сутки, 30 дней | оставить |

Параметр `mailgate` = максимум писем за один проход. При 100–500
пользователях и утреннем пике 10 писем/10 минут может не хватить: очередь
будет разгребаться часами. 50 писем каждые 5 минут — безопасный запас.

**Режим запуска — CLI.** В режиме «GLPI» автодействия выполняются только
когда кто-то открывает страницы GLPI: ночью и в выходные почта собираться не
будет, а после перерыва прилетит пачка заявок с неверными датами. Настройка
cron на сервере (выполняет системный администратор, от пользователя
веб-сервера):

```cron
* * * * * /usr/bin/php /var/www/glpi/front/cron.php >> /var/log/glpi/cron.log 2>&1
```

GLPI сам решает, какие задачи запускать по их частоте; запускать cron чаще
раза в минуту не нужно. После настройки CLI-режима каждому автодействию
выставляется «Режим выполнения: CLI».

## 8. Защита от петель (обязательный раздел)

### 8.1. Что GLPI фильтрует сам

| Механизм | Что отсекает | Ограничение |
|---|---|---|
| Проверка `Message-Id` собственного экземпляра | письмо, отправленное этим же GLPI (заголовок вида `GLPI_<uuid>-Ticket-123-...`) | работает только для писем, реально сформированных GLPI |
| Проверка ответа на письмо другого GLPI | ветки чужого экземпляра GLPI | нужно, когда два GLPI переписываются |
| Чёрный список адресов (Настройка → Справочники → Чёрные списки → Email) | письма с перечисленных адресов | нужно заполнить руками |
| Название коллектора, если это email | письма от самого ящика поддержки | поэтому в поле «Название» указываем адрес ящика |

### 8.2. Чего GLPI **не** фильтрует сам

GLPI **не отбрасывает автоматически** письма с заголовками
`Auto-Submitted: auto-replied`, `X-Auto-Response-Suppress`, отчёты о
недоставке и письма от `no-reply@`. Эти заголовки только **доступны как
критерии правил**. Без правил автоответ Outlook «Я в отпуске» превращается в
обычную заявку, а отчёт о недоставке — в ещё одну.

Настраивается в: **Администрирование → Правила → Правила назначения заявки,
созданной через почтовый сборщик** (RuleMailCollector).

Доступные критерии (точные названия в интерфейсе):

- Заголовок письма `Subject` / `From` / `To` / `In-Reply-To`
- Заголовок письма `Auto-Submitted`
- Заголовок письма `X-Auto-Response-Suppress`
- Заголовок письма `X-Priority`, `X-UCE-Status`, `Received`
- «Полные заголовки письма» (`_headers`) — регулярное выражение по всему блоку заголовков
- Получатель (коллектор), заявитель, группы заявителя, известный домен, профиль

Доступные действия (важные):

- **«Отклонить письмо (без ответа на email)»** — `_refuse_email_no_response`
- «Отклонить письмо (с ответом на email)» — `_refuse_email_with_response`
- Назначить сущность (в т.ч. по домену/по тегу/по сущности пользователя)

### 8.3. Обязательный набор правил (создать ДО активации коллектора)

Все правила — с действием **«Отклонить письмо (без ответа на email)»**,
размещаются **первыми** в списке правил, каждое со «Стоп обработки правил».

| № | Название правила | Критерий | Условие | Значение |
|---|---|---|---|---|
| 1 | `Отклонить: Auto-Submitted` | Заголовок `Auto-Submitted` | регулярное выражение | `/^auto-(replied\|generated\|notified)/` |
| 2 | `Отклонить: X-Auto-Response-Suppress` | Заголовок `X-Auto-Response-Suppress` | содержит | `All` (второе правило — на `OOF`) |
| 3 | `Отклонить: отправитель no-reply` | Заголовок `From` | регулярное выражение | `/(no[-_.]?reply\|do[-_.]?not[-_.]?reply\|postmaster\|mailer[-_.]?daemon\|bounce)/` |
| 4 | `Отклонить: отчёты о недоставке` | Заголовок `Subject` | регулярное выражение | `/(undeliverable\|delivery status notification\|returned mail\|не доставлено\|возврат сообщения)/` |
| 5 | `Отклонить: автоответы об отсутствии` | Заголовок `Subject` | регулярное выражение | `/(out of office\|automatic reply\|автоответ\|отсутствую\|в отпуске)/` |
| 6 | `Отклонить: рассылки (List-Id)` | Полные заголовки письма | регулярное выражение | `/^(list-id\|list-unsubscribe\|precedence:\s*(bulk\|list\|junk))/m` |
| 7 | `Отклонить: сам ящик поддержки` | Заголовок `From` | содержит | `<SUPPORT_MAILBOX>` |

**Синтаксис регулярных выражений в правилах GLPI:** шаблон пишется
**вместе с ограничителями** — `/шаблон/`. GLPI добавляет к нему модификаторы
`s` и `i` самостоятельно, поэтому учитывать регистр не нужно, а точка
совпадает с переводом строки (важно для критерия «Полные заголовки письма»).
Шаблон без ограничителей приводит к ошибке `Invalid regular expression` в
журнале и к правилу, которое молча никогда не срабатывает.

Пояснения:

- Правила 1–2 покрывают корректно оформленные автоответы (Exchange, Outlook,
  большинство почтовых систем). Правила 3–6 — «грязную» реальность, где
  заголовки не проставлены.
- Правило 6 (`Precedence: bulk`, `List-Id`) отсекает маркетинговые рассылки,
  подписки и уведомления SaaS-сервисов.
- **Действие — строго «без ответа».** Вариант «с ответом» заставляет GLPI
  отправить письмо обратно отправителю; если отправитель — автоответчик,
  получается взаимный обстрел. GLPI помечает такой отказ заголовком
  `Auto-Submitted: auto-replied`, что обычно останавливает петлю, но
  полагаться на вежливость чужого автоответчика не стоит.
- Дополнительно: адреса `noreply@...`, `postmaster@...`, `<SUPPORT_MAILBOX>`
  и адреса систем мониторинга занести в **Настройка → Справочники → Чёрные
  списки → Email**. Письма от них отбрасываются до обработки правил.

### 8.4. Что будет, если этого не сделать

Сценарий (наблюдается регулярно):

1. Сотрудник в отпуске включил автоответ на своём ящике.
2. Он же (или коллега, поставивший его в копию) пишет в поддержку.
3. GLPI создаёт заявку и шлёт уведомление «Заявка #123 зарегистрирована» на
   его адрес.
4. Его автоответчик отвечает на уведомление → письмо приходит в
   `<SUPPORT_MAILBOX>` → GLPI добавляет фолоуап в заявку #123 → фолоуап
   порождает новое уведомление заявителю → его автоответчик отвечает снова.

Цикл ограничен только частотой `mailgate`. При частоте 5 минут это ~288
итераций в сутки на одну петлю; при частоте 1 минута — 1440. На каждой
итерации: письмо наружу, письмо внутрь, запись в БД, запись в очереди
уведомлений. Практические последствия:

- тысячи фолоуапов в одной заявке, заявка становится нечитаемой;
- очередь уведомлений растёт быстрее, чем разбирается, — **останавливаются
  все остальные уведомления**, включая уведомления о новых заявках;
- почтовый провайдер включает rate limit или временно блокирует ящик
  (для Microsoft 365 это срабатывает на порядке 10 тыс. писем/сутки);
- домен компании попадает в спам-листы при внешних адресатах.

Если петля уже началась (порядок действий):

1. Настройка → Получатели → коллектор → **Активен: Нет** (останавливает вход).
2. Настройка → Автодействия → `queuednotification` → **Отключить**
   (останавливает выход).
3. Определить заявку/адрес-источник: Настройка → Уведомления → «Очередь
   уведомлений», отсортировать по получателю.
4. Занести адрес в чёрный список, создать недостающее правило из 8.3.
5. Очистить очередь уведомлений (массовое удаление в интерфейсе очереди).
6. Закрыть/очистить пострадавшую заявку, включить обратно `queuednotification`,
   затем коллектор.

### 8.5. Режим обкатки

До объявления адреса пользователям:

- `Собирать только непрочитанные письма` = Да;
- коллектор активируется на 1 рабочий день, поток проверяется вручную через
  вкладку **«Получить письма»** (ручной запуск без записи в БД для отладки);
- ежедневно просматривается список **«Отклонённые письма»**
  (`front/notimportedemail.php`, доступен из меню получателей) — там видно
  причину отказа: пользователь не найден, нет прав, не сработало ни одного
  правила, ошибка операции;
- папка `<IMAP_FOLDER_REFUSED>` просматривается глазами: там лежат исходные
  письма, отклонённые правилами.

## 9. Привязка ответа к существующей заявке

Два механизма, в порядке применения:

1. **Заголовки `In-Reply-To` / `References`.** GLPI подставляет в исходящие
   уведомления `Message-Id` собственного формата
   (`GLPI_<uuid>-<itemtype>-<items_id>-...`). Корректный почтовый клиент
   возвращает его в `In-Reply-To`. Это самый надёжный путь, работает даже
   если пользователь изменил тему.
2. **Разбор темы.** Если заголовков нет (веб-интерфейсы почты, пересылка
   через мессенджер-шлюз, копирование текста в новое письмо), GLPI ищет в
   теме шаблон `[<любой текст> #<число>]` и берёт номер заявки. Отсюда
   требование раздела 5.1: префикс уведомлений и номер заявки в теме.

Дополнительные условия, без которых фолоуап не добавится:

- заявка с этим номером существует и не удалена;
- отправитель — участник заявки (заявитель, наблюдатель, назначенный,
  поставщик) либо его адрес указан как альтернативный email в заявке.
  Иначе GLPI не добавляет фолоуап, а создаёт новую заявку, **связанную** с
  исходной.

Типовые последствия для пользователей (включить в инструкцию из `guides/`):

- «Ответить» — фолоуап в существующую заявку;
- «Создать новое письмо» с новой темой — новая заявка;
- переслать старую переписку с темой `[HOFI #0000123]` — попадёт фолоуапом в
  заявку 123, даже если содержание совсем другое. Это ожидаемое поведение
  разбора темы.

## 11. Типовые ошибки

| Симптом | Причина | Проверка / решение |
|---|---|---|
| «Получатели с ошибками» в шапке GLPI | коллектор не смог подключиться, счётчик `errors` > 0 | `checks.md` → IMAP: сеть, пароль, сертификат. После успешного прогона счётчик обнуляется |
| `Cannot connect` / таймаут | закрыт порт с сервера GLPI, DNS резолвится не туда | `openssl s_client`, `getent hosts` |
| `AUTHENTICATIONFAILED` | пароль сменился / Basic Auth отключён (M365) | сменить пароль в коллекторе; перейти на OAuth (6.4) |
| Ошибка проверки сертификата | самоподписанный сертификат или неполная цепочка на почтовом сервере | добавить корневой CA в доверенные на сервере GLPI. `novalidate-cert` — только на время диагностики |
| Письма собираются, заявки не создаются | все письма попадают в «Отклонённые письма» | открыть список отклонённых: причина указана явно (пользователь не найден / нет прав / не сработало ни одного правила) |
| Письма обрабатываются повторно, дубли заявок | GLPI не смог удалить/переместить письмо (нет прав на папку, папки не существует) | проверить существование `<IMAP_FOLDER_ACCEPTED>` / `<IMAP_FOLDER_REFUSED>`, права ящика |
| Папка не находится, хотя она есть | кириллица в имени папки (кодировка UTF-7 IMAP) | использовать латинские имена папок: `GLPI/accepted` |
| Вложения не попадают в заявку | расширение не заведено в «Типы документов»; `files/_tmp` не доступен на запись; лимит = 0 | `files/_log/mailgate.log`, справочник типов документов, `ls -ld files/_tmp` |
| Заявки создаются, уведомления не уходят | не настроен SMTP; отключено автодействие `queuednotification`; письма застряли в очереди | Настройка → Уведомления → Очередь уведомлений |
| Ответ пользователя создаёт новую заявку вместо фолоуапа | в теме нет `[TAG #номер]`, шаблон уведомления изменён; отвечает не участник заявки | вернуть префикс (5.1), проверить состав участников заявки |
| Заявки приходят от «неизвестного» заявителя | email пользователя не синхронизирован из AD | [`ldap-ad.md`](ldap-ad.md) |
| Даты заявок = времени сбора, а не письма | выключено «Использовать дату письма» | включить в коллекторе |
| Ночью письма не собираются | автодействия в режиме «GLPI» | перевести `mailgate` в режим CLI, настроить cron (раздел 7) |
| Взрывной рост фолоуапов в одной заявке | петля автоответчика | раздел 8.4 |
| В заявках мусорные картинки-подписи | inline-изображения импортируются как документы | ожидаемое поведение; регламент уборки либо запрет типа изображения в справочнике |

Порядок диагностики всегда один: **сеть и порт → учётные данные → права
сервисной учётки → конфигурация GLPI → логи (`files/_log/mailgate.log`,
`files/_log/php-errors.log`, `cron.log`) → автодействия (статус, последний
запуск)**.

## 12. Откат

Откат почтового канала выполняется за минуты и не требует восстановления
БД, если следовать порядку.

1. **Немедленная остановка приёма:** Настройка → Получатели → коллектор →
   «Активен: Нет». Письма остаются в ящике, ничего не теряется.
2. **Остановка исходящих:** Настройка → Автодействия → `queuednotification`
   → «Отключить». Уведомления копятся в очереди, не уходят.
3. **Полное отключение уведомлений** (если проблема в SMTP): Настройка →
   Уведомления → «Использовать уведомления по email» = Нет.
4. **Удаление ошибочных заявок**, созданных за время инцидента: список
   заявок → фильтр по дате создания и по источнику запроса «E-Mail» →
   массовое удаление в корзину (не «окончательно»: корзина позволяет
   передумать).
5. **Возврат писем на разбор людьми:** письма остались в ящике и в папках
   `<IMAP_FOLDER_ACCEPTED>`/`<IMAP_FOLDER_REFUSED>` — их можно вернуть в
   INBOX средствами почтового клиента и обработать вручную.
6. **Откат конфигурации коллектора:** значения полей до изменения видны в
   журнале (вкладка «Исторические данные» объекта получателя).
7. Только после устранения причины — обратная последовательность:
   правила → ручной прогон → активация коллектора → включение
   `queuednotification`.

Перед любыми изменениями почтовой конфигурации на продуктиве — снимок
(dump) БД GLPI; это требование общее для всего Релиза 1.

## 13. Отличия GLPI 11

| Тема | GLPI 10.x | GLPI 11.x |
|---|---|---|
| Форма получателя | старый HTML-рендеринг, набор полей тот же | форма перенесена на Twig; состав полей и логика сбора совпадают |
| Протоколы соединения | IMAP/POP, фиксированный список | список протоколов расширяется плагинами (`getMailServerProtocols`) |
| Правила сборщика | RuleMailCollector с критериями по заголовкам | без изменений по составу критериев |
| Анти-петля | `Message-Id` с UUID экземпляра | без изменений |
| Автодействия | `mailgate`, `mailgateerror`, `queuednotification` | те же имена |
| CLI cron | `php front/cron.php` | `php front/cron.php` сохранён |
| OAuth для IMAP | плагин `oauthimap` | больше возможностей в ядре/плагинах провайдеров |

Для Релиза 1 существенных различий нет: конфигурация переносится один в один.

## 14. Секреты, которые нужно завести

В репозиторий не попадает ни одно реальное значение. Ниже — что завести в
менеджере паролей компании и с какими минимальными правами.

| Плейсхолдер | Что это | Минимальные права | Где используется |
|---|---|---|---|
| `<IMAP_PASSWORD>` | пароль ящика `<SUPPORT_MAILBOX>` | только доступ к своему ящику по IMAP; без прав на другие ящики, без прав администратора почтовой системы, без интерактивного входа на рабочие станции | поле «Пароль» получателя в GLPI |
| `<SMTP_PASSWORD>` | пароль учётной записи отправки | право отправки (submit) от адреса `<SUPPORT_MAILBOX>`; без прав «отправлять от имени любого пользователя» | Настройка → Уведомления → SMTP |
| `<OAUTH_CLIENT_ID>` / `<OAUTH_CLIENT_SECRET>` / `<OAUTH_TENANT_ID>` | только при варианте OAuth (6.4) | delegated `IMAP.AccessAsUser.All`, `SMTP.Send` на один ящик; **не** application-permission на весь тенант | плагин `oauthimap` / SMTP+OAUTH |

Дополнительно зафиксировать письменно:

- владелец ящика `<SUPPORT_MAILBOX>` и процедура смены пароля (с обязательным
  обновлением в GLPI — иначе канал встанет молча);
- срок действия пароля;
- кто имеет право включать/выключать коллектор.
