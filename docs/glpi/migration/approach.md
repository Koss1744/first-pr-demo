# Подход к миграции данных в GLPI

**Статус:** подготовлено к выполнению (миграция не начата)
**Дата:** 2026-09-15
**Инстанс:** https://sd.hofi.su
**Применяется после:** утверждения решений в [decision.md](decision.md)
**Связанные документы:** [decision.md](decision.md), [inventory-questionnaire.md](inventory-questionnaire.md), [../plan.md](../plan.md) (этап 2.7, трек В), [../risks.md](../risks.md) (R-03, ОК-5)

Документ описывает, **как** будет устроена миграция, когда заказчик решит,
что переносить. Сам по себе он не запускает работы и не требует доступа к
данным. Прямого доступа к инстансу и к источникам у нас сейчас нет.

## 1. Место миграции в плане проекта

**Принцип: миграция не входит в критический путь Релиза 1 (приём заявок с почты).**

Календарь синхронизирован с [../plan.md](../plan.md): миграция — это трек В,
этап 2.7, стартующий только после решения ОК-5.

| Период | Что идёт в проекте | Миграция (параллельный трек В) |
|---|---|---|
| 2026-09-15 … 09-18 | Предстартовые зависимости Релиза 1 (ОК-1, ОК-2) | Опросник отправлен заказчику. **Ответ на вопрос 5.4 (все ли в AD) нужен к 09-18** |
| 2026-09-21 … 10-02 | Работы Релиза 1 (этапы 1.1–1.9) | Сбор ответов опросника, черновик решений по типам данных. Импортов нет |
| 2026-10-05 … 10-16 | Запуск на пилотную группу, гиперкеа, выход из Релиза 1 | **Полный мораторий на импорты.** 2026-10-16 — крайний срок решения ОК-5 |
| 2026-10-19 … 11-13 | Релиз 2: процессы (2.2), права (2.3), инвентаризация (2.6) | Получение выгрузок, `field-mapping.md`. **Пробный прогон (10 записей)** на тестовом контуре — после закрытия 2.3 |
| 2026-11-16 … 11-27 | Формы (2.4), SLA (2.5) | **Полный прогон на тестовом контуре** + сверка по числам |
| 2026-11-30 … 12-11 | Продолжение 2.4, 2.5, 2.8 | **Продуктивный импорт** активов, лицензий, договоров, КБ + сверка + акт |
| с 2026-12-14 | Пилот (2.9), обучение (2.10) | История заявок — только при сценарии C по ОК-5 |

Четыре правила, защищающие дату Релиза 1:

1. **Единственная зависимость Релиза 1 от этого блока — пользователи и
   оргструктура.** Они закрываются интеграцией с AD (этапы 1.2–1.3, зона
   `glpi-integrator`) и ручным вводом десятков записей справочников, а не
   импортом. Если по миграции не будет ни одного ответа, Релиз 1 всё равно
   выходит 2026-10-16.
2. **Мораторий на продуктивные импорты с 2026-10-05 по 2026-10-16** — неделя
   запуска и гиперкеа. Иначе сбой импорта и сбой запуска сливаются в один
   инцидент, и разбираться придётся в двух местах одновременно.
3. **Пробный и тестовый прогоны идут только на тестовом контуре** и не
   касаются продуктивного инстанса до выхода из Релиза 1.
4. **Миграция ведётся отдельным человеком** (0,5 FTE, трек В). Если её берёт
   на себя инженер Релиза 1 — правило 1 перестаёт работать, и миграция
   становится в критический путь через ресурс, а не через данные. Это самый
   частый способ уронить дату запуска.

Этап 2.7 не может стартовать до закрытия 2.3 (сущности, профили, права):
импорт в непонятную структуру сущностей означает переделку всего объёма.

## 2. Порядок переноса (нарушать нельзя)

Порядок задан зависимостями по внешним ключам: каждый следующий шаг
ссылается на предыдущие. Импорт активов до местоположений создаст активы
без привязки, и переделывать придётся всё.

| # | Что | Зависит от | Инструмент | Оценка |
|---|---|---|---|---|
| 1 | Справочники и оргструктура: сущности, местоположения, группы, типы, модели, производители | — | Ручной ввод + CSV | 0,5–2 д. |
| 2 | Пользователи | 1 | **LDAP-синхронизация**, CSV только для локальных учёток | 0,5–2 д. |
| 3 | Активы: компьютеры, мониторы, сетевое, печать, телефоны | 1, 2 | GLPI Agent + DataInjection | 2–5 д. |
| 4 | ПО и лицензии | 3 | DataInjection | 1–2 д. |
| 5 | Поставщики, договоры, привязка договоров к активам | 1, 3 | DataInjection + REST API для связей | 0,5–2 д. |
| 6 | Документы и вложения | 5 | **Только REST API** | 0,5–1 д. |
| 7 | База знаний | 1 | Ручной перенос / REST API | 1–4 д. |
| 8 | История заявок | всё выше | REST API | 5–15+ д. |

Каждый шаг закрывается сверкой по числам (раздел 7) до начала следующего.
Незакрытая сверка — стоп, а не «догоним потом».

## 3. Ключи дедупликации

Ключ дедупликации определяется **до** первого прогона и фиксируется здесь.
Без него повторный запуск импорта создаёт дубли, а не обновляет записи.
В DataInjection ключ задаётся полем поиска существующей записи в модели
импорта, режим — «обновить, если найдено, иначе создать».

| Объект | Ключ (по приоритету) | Резервный ключ | Если ключ пуст |
|---|---|---|---|
| `Computer` | Серийный номер (`serial`) | Инвентарный номер (`otherserial`) → имя хоста (`name`) | В карантин, без импорта |
| `Monitor`, `Peripheral`, `Printer` | Серийный номер | Инвентарный номер | В карантин |
| `NetworkEquipment` | Серийный номер | Имя + MAC управляющего интерфейса | В карантин |
| `Phone` | Инвентарный номер | Серийный номер | В карантин |
| `SoftwareLicense` | Название ПО + номер лицензии (`serial`) | Название + договор | Импорт, пометка «уточнить» |
| `User` | `login` (`samaccountname` из AD) | Корпоративный e-mail | Не импортировать |
| `Supplier` | ИНН | Название в точности | Импорт с пометкой |
| `Contract` | Номер договора + поставщик | Номер договора | Не импортировать |
| `Location` | Полный путь «Город > Адрес > Этаж > Кабинет» | — | В корень сущности |
| `KnowbaseItem` | Заголовок | — | Не импортировать |
| `Ticket` | Внешний номер в поле `Комментарии` / доп. поле | — | Не импортировать |

**Правило карантина:** запись без значения ключа не импортируется молча и не
выбрасывается. Она попадает в `unmapped.md` с причиной и показывается
заказчику. Типичный объём карантина — 3–10% строк из Excel-учётов.

**Отдельно про серийные номера:** значения `To be filled by O.E.M.`,
`System Serial Number`, `Default string`, `0000000000`, `None`, пустая строка
считаются отсутствующими и не могут быть ключом — иначе весь такой парк
схлопнется в один актив. Список стоп-значений фиксируется в `field-mapping.md`.

## 4. Три прогона

Ни один импорт не идёт в продуктив без двух предшествующих прогонов.

### Прогон 1 — пробный, 10 записей

- **Где:** тестовый контур.
- **Что:** 10 записей, отобранных не случайно: 5 типовых + 5 проблемных
  (пустые поля, кириллица, длинные названия, дубли, нестандартные даты).
- **Цель:** проверить маппинг и кодировку, а не производительность.
- **Проверяем:** все ли поля встали на места; не поехала ли кодировка
  (CSV — UTF-8 без BOM, разделитель `;`, кавычки `"`); как обработались
  пустые значения; отработал ли ключ дедупликации при **повторном** запуске
  того же файла — количество записей не должно вырасти.
- **Выход:** утверждённый `field-mapping.md`, первая версия `unmapped.md`.
- **Длительность:** 2–4 часа на тип данных.

### Прогон 2 — полный на тестовом контуре

- **Где:** тестовый контур, база восстановлена из свежей копии продуктива.
- **Что:** весь объём целиком.
- **Цель:** получить реальные числа расхождений и реальное время импорта.
- **Проверяем:** полную сверку по разделу 7; ручную выборку 20 записей;
  время выполнения — оно определит окно продуктивного импорта.
- **Выход:** протокол сверки, финальный `unmapped.md`, согласие владельца
  данных на продуктивный импорт.
- **Длительность:** от часов до суток в зависимости от объёма.

### Прогон 3 — продуктивный

- **Когда:** не раньше чем через неделю после Релиза 1, в нерабочее время.
- **Предусловия (все обязательны):**
  1. бэкап БД снят и **проверен восстановлением** на тестовом контуре;
  2. команда отката записана и проверена (раздел 6);
  3. прогон 2 завершён, расхождения объяснены и приняты;
  4. владелец данных согласовал; известно, кто принимает результат;
  5. импорт выполняется тем же файлом и той же моделью DataInjection,
     что и в прогоне 2 — без правок «на ходу».
- **После:** сверка по числам в тот же вечер, не «утром посмотрим».

## 5. Пометка импортированных записей

Без пометки импортированные записи неотличимы от заведённых руками, и
выборочный откат невозможен. Применяются **три** независимых механизма —
каждый решает свою задачу.

**1. Технический пользователь-импортёр.** Все импорты выполняются от
отдельной учётной записи `svc-migration` (профиль с правами только на
нужные объекты). GLPI пишет автора в журнал (`glpi_logs`), поэтому любую
запись можно отнести к миграции даже без пометок в полях. Живые люди этой
учёткой не пользуются.

**2. Маркер в поле «Комментарии».** В конец комментария добавляется строка
фиксированного формата:

```
[MIG src=<система> batch=<идентификатор партии> date=<ГГГГ-ММ-ДД> id=<ID в источнике>]
```

Пример: `[MIG src=excel-assets batch=assets-03 date=2026-11-12 id=A-01847]`

Формат даёт сразу и признак импорта, и связь с источником, и партию для
точечного отката. Поиск `Комментарии содержит [MIG` находит все записи.

**3. Журнал соответствий (ledger).** На каждую партию — CSV-файл в репозитории
`docs/glpi/migration/ledger/<batch>.csv`:

```
source_id;glpi_itemtype;glpi_id;imported_at;batch;checksum_key
```

Ledger заполняется из ответов API либо выгружается SQL-запросом на чтение
сразу после импорта. **Это основной инструмент точечного отката** и основа
сверки: по нему видно, что ровно N записей источника стали N записями GLPI.

Дополнительно, если заказчик согласится на плагин `Fields`: отдельное поле
`Источник миграции` у активов. Плюс — фильтрация и отчёты без разбора
комментариев. Минус — плагин надо поддерживать при обновлениях GLPI, поэтому
как обязательный механизм он не закладывается.

## 6. Обратимость и откат

### Перед продуктивным импортом

```bash
# Полный дамп БД GLPI (выполняет администратор на сервере sd.hofi.su)
mysqldump --single-transaction --routines --triggers \
  -u <DB_USER> -p'<DB_PASSWORD>' <DB_NAME> \
  > /backup/glpi_pre_<batch>_$(date +%Y%m%d_%H%M).sql

# Обязательно: проверить бэкап восстановлением на ТЕСТОВОМ контуре
mysql -u <DB_USER> -p'<DB_PASSWORD>' <DB_NAME_TEST> < /backup/glpi_pre_<batch>_<ts>.sql
```

Непроверенный бэкап бэкапом не считается. Дополнительно сохраняются файлы
вложений `files/` — они не лежат в БД.

### Откат-1: полное восстановление БД (импорт пошёл не так)

```bash
# Инстанс выводится в режим обслуживания, затем:
mysql -u <DB_USER> -p'<DB_PASSWORD>' <DB_NAME> < /backup/glpi_pre_<batch>_<ts>.sql
```

Цена: теряются все изменения с момента бэкапа, включая заявки, созданные
пользователями. Поэтому продуктивный импорт делается в нерабочее время,
а окно «бэкап → импорт → сверка» держится минимальным.

### Откат-2: точечное удаление (импорт прошёл, но данные признаны негодными)

Предпочтительный сценарий — он не затрагивает работу пользователей.
По `ledger/<batch>.csv` записи удаляются через REST API поштучно:

```
DELETE /apirest.php/Computer/<glpi_id>    → в корзину
DELETE /apirest.php/Computer/<glpi_id>?force_purge=true   → окончательно
```

Ограничение: если после импорта на запись успели сослаться (например, на актив
повесили заявку), точечное удаление оставит битую ссылку. Поэтому точечный
откат допустим только в окне до возобновления работы пользователей; после —
только Откат-1 или ручной разбор.

### Чего делать нельзя

**Прямые `DELETE`/`UPDATE`/`INSERT` в базу GLPI запрещены.** Ломаются связи
`*_items`, журналы (`glpi_logs`), счётчики и индекс поиска. Прямой SQL
допустим **только на чтение** и только для сверки.

## 7. Сверка результата числами

Импорт считается принятым, только если сошлись все четыре проверки.
Результат оформляется протоколом `reconciliation-<batch>.md`.

**Проверка 1 — количество на входе и выходе.**

| Показатель | Как считается |
|---|---|
| Строк в источнике | `wc -l` минус заголовок |
| Строк отправлено в импорт | после фильтрации и карантина |
| Создано в GLPI | по ledger и по счётчику интерфейса |
| Обновлено существующих | из отчёта DataInjection |
| В карантине | строк в `unmapped.md` |

Тождество, которое обязано выполняться:

```
строк в источнике = создано + обновлено + карантин + осознанно исключено
```

Любое расхождение объясняется построчно. «Потерялось несколько записей» —
не результат сверки, а её отсутствие.

**Проверка 2 — контрольные суммы по ключевым полям.** Сравниваются множества
ключей источника и приёмника, а не только их мощность:

```sql
-- Пример для активов; SQL ТОЛЬКО НА ЧТЕНИЕ
SELECT COUNT(*) AS total,
       COUNT(DISTINCT serial) AS uniq_serial,
       SUM(CASE WHEN serial IS NULL OR serial = '' THEN 1 ELSE 0 END) AS no_serial
FROM glpi_computers
WHERE is_deleted = 0 AND comment LIKE '%[MIG %batch=assets-03%';
```

Сверяется: общее число, число уникальных серийников (должно совпадать с
источником — расхождение означает схлопывание дублей), распределение по
местоположениям и по сущностям, суммы по числовым полям (например, суммарная
стоимость активов должна совпасть с источником до копейки).

**Проверка 3 — выборочная ручная сверка 20 записей.** Отбор не случайный:

- 5 типовых записей;
- 5 с пустыми и нестандартными значениями;
- 5 с кириллицей, длинными названиями и спецсимволами (проверка кодировки);
- 5 с наибольшим числом связей (актив с договором, лицензией, пользователем).

Сверяются все поля, а не только название. Результат — таблица в протоколе
с отметкой по каждой записи. Сверку подписывает владелец данных.

**Проверка 4 — целостность связей.** Импорт может создать записи и не создать
связи, и по счётчику это незаметно:

```sql
-- Активы без местоположения и без пользователя среди импортированных
SELECT COUNT(*) FROM glpi_computers
WHERE is_deleted = 0 AND comment LIKE '%[MIG %batch=assets-03%'
  AND (locations_id = 0 OR (users_id = 0 AND groups_id = 0));
```

Порог приёмки задаётся заранее, до импорта (например, «не более 5% активов
без местоположения»), и фиксируется в `field-mapping.md`.

## 8. Инструменты: что для чего

| Инструмент | Для чего подходит | Для чего не подходит |
|---|---|---|
| **Штатный CSV-импорт GLPI** | Небольшие справочники, разовая загрузка простых списков (местоположения, производители, модели). Ничего ставить не нужно | Сложные объекты, связи, обновление существующих записей, контроль дублей. Набор поддерживаемых объектов ограничен |
| **Плагин DataInjection** | **Основной инструмент.** Активы, лицензии, договоры, поставщики. Сохраняемые модели импорта (повторяемость прогонов), поиск существующей записи по ключу, режим обновления, отчёт об ошибках построчно | Вложения и файлы. Сложные многосвязные структуры. Заявки с перепиской. Проверить совместимость версии плагина с версией GLPI — до планирования работ |
| **REST API (`/apirest.php`)** | Связи «многие ко многим», вложения и документы, база знаний с HTML, заявки с последовательностью «тикет → наблюдатели → комментарии → решение», а также **точечный откат** по ledger | Массовая загрузка десятков тысяч записей: медленно, нужен контроль лимитов и батчей по 50–100 объектов с паузами |
| **Прямой SQL** | **Только чтение:** сверка, контрольные суммы, выгрузка ledger, поиск дублей | **Любая запись запрещена.** Ломает связи, журналы и поиск |
| **GLPI Agent** | Не миграция, а альтернатива ей: технические данные активов собираются точнее и без ручного труда | Финансовые и учётные поля: инвентарный номер, МОЛ, стоимость, гарантия, договор |

Практическое сочетание для активов: **агент собирает парк → DataInjection
догружает финансовые поля по ключу `serial` в режиме обновления → REST API
проставляет связи с договорами.** Так тяжёлая часть делается автоматически,
а импортом добираются только те поля, которых больше взять неоткуда.

## 10. Безопасность и доступы

- В артефактах — только плейсхолдеры: `<DB_USER>`, `<DB_PASSWORD>`,
  `<API_TOKEN>`. Реальные значения в репозиторий не попадают.
- Выгрузки из источников содержат персональные данные и в git не коммитятся.
  Обрабатываются вне репозитория, доступ — только участникам миграции,
  удаляются после приёмки.
- Токен API для `svc-migration` выдаётся на время миграции и отзывается
  после приёмки продуктивного импорта.
- Перед выгрузкой персональных данных подтвердить у заказчика правовое
  основание (вопрос 6.3 опросника).
