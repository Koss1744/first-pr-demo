Статус: черновик на согласование
Инстанс: https://sd.hofi.su
Версия: **GLPI 10.x** (допущение; зависящие от версии решения помечены явно)
Масштаб: 100–500 пользователей

Связанные артефакты: [`categories.md`](categories.md),

# 0. Цель и границы

## Цель Релиза 1

**Прекратить приём заявок в мессенджеры и на личную почту.** Всё
остальное — вторично. Успех Релиза 1 измеряется долей обращений,
попавших в GLPI, а не полнотой процессов.

## Что осознанно НЕ делаем в Релизе 1

Это решения, а не пробелы:

| Не делаем | Почему |
|---|---|
| Полный каталог услуг | Требует согласования владельцев вне ИТ — недели. Блокирует запуск. См. `service-catalog.md`, раздел 1 |
| Процесс управления изменениями (`Change`) | Отдельного процесса изменений в компании нет. Заводить объект ради ITIL — создавать пустой раздел |
| Управление проблемами (`Problem`) | Нет статистики повторяющихся инцидентов. Появится после 2–3 месяцев данных |
| OLA между линиями | Нет измеренного времени передачи L1→L2. Вторая система просрочек без пользы |
| Инвентаризация активов (GLPI Agent) | Не нужна для приёма заявок. Отдельный контур внедрения |
| Миграция истории заявок | Решение не принято. См. RE-Q3 |
| Управление конфигурациями (CMDB) | Следствие инвентаризации, которой нет |
| Согласования (валидация заявок) | Нет утверждённого процесса согласования |
| SSO | AD-аутентификации по LDAP достаточно для старта |
| Плагины (в т.ч. Formcreator) | Каждый плагин — зависимость при обновлении; на старте обходимся ядром |
| 5 уровней приоритета, матрица 5×5 | Упрощены до 3. См. `sla-matrix.md`, раздел 2 |
| 24×7 SLA | Нет дежурства вне рабочих часов. Обещать нельзя |
| Структура сущностей по подразделениям | Самое дорогое в откате решение. Принимаем на данных Релиза 1 |

# 1. Требования Релиза 1

Срок: 1–2 недели настройки. Каждое требование — с объектом GLPI и
разделом интерфейса, чтобы администратор мог выполнить без уточнений.

## 1.2 Каналы приёма заявок

Цель Релиза 1 достигается только если у пользователя есть куда писать.
Каналов ровно два — портал и почта.

| № | Требование | Объект GLPI | Раздел интерфейса | Приоритет |
|---|---|---|---|---|
| R1-CH-01 | Портал самообслуживания доступен всем сотрудникам по AD-логину | `Profile` (упрощённый интерфейс) | см. `roles-matrix.md` | **Блокирующее** |
| R1-CH-02 | Настроен общий ящик поддержки (`<SUPPORT_MAILBOX>`), письма превращаются в заявки | `MailCollector` | Настройка → Приёмники | **Блокирующее** |
| R1-CH-03 | Письмо от известного по email пользователя создаёт заявку от его имени | `MailCollector` + сопоставление по email | Настройка → Приёмники | Обязательно |
| R1-CH-04 | Письмо с неизвестного адреса не создаёт заявку «ниоткуда» (отклоняется или падает в отдельную категорию) | `RuleMailCollector` | Администрирование → Правила → Правила для сборщика почты | Обязательно |
| R1-CH-05 | Ответ пользователя на письмо-уведомление дописывается в существующую заявку, а не создаёт новую | `MailCollector` (распознавание номера заявки в теме) | Настройка → Приёмники | Обязательно |
| R1-CH-06 | Заявки по телефону заводит первая линия от имени сотрудника | право «Создать заявку для другого» | `Profile` `HOFI L1` | Обязательно |
| R1-CH-07 | Личные ящики ИТ и рабочие чаты: автоответ со ссылкой на портал | вне GLPI | план коммуникаций (`glpi-pm`) | Обязательно |

> Автоматическое создание учётной записи по письму с неизвестного адреса
> **отключить**. Иначе база засоряется контрагентами и спамом, а заявки
> получают несуществующих заявителей.

## 1.7 Уведомления

Без уведомлений пользователь не видит движения по заявке и возвращается
в мессенджер. Это функциональное требование, а не «косметика».

| № | Требование | Объект GLPI | Раздел интерфейса | Приоритет |
|---|---|---|---|---|
| R1-NTF-01 | Включены уведомления по email, задан адрес отправителя и SMTP | Конфигурация уведомлений | Настройка → Уведомления → Настройка уведомлений по email | **Блокирующее** |
| R1-NTF-02 | Заявителю: «Заявка зарегистрирована» с номером и ссылкой | `Notification` + `NotificationTemplate` | Настройка → Уведомления → Уведомления | Обязательно |
| R1-NTF-03 | Заявителю: «Добавлен комментарий» (только публичный) | `Notification` | там же | Обязательно |
| R1-NTF-04 | Заявителю: «Заявка решена» с предложением подтвердить | `Notification` | там же | Обязательно |
| R1-NTF-05 | Группе-исполнителю: «Назначена новая заявка» | `Notification`, получатель «Группа — назначенная» | там же | Обязательно |
| R1-NTF-06 | Руководителю ИТ: «Нарушен срок решения» | `SlaLevel` + `Notification` | Настройка → Уровни обслуживания | Обязательно |

> Проверить, что адрес отправителя уведомлений и адрес сборщика почты

> создания заявок. Классический сбой первого дня.

# 2. Критерии приёмки Релиза 1

Релиз 1 считается закрытым, когда **все** пункты выполнены. Проверяет
`glpi-qa`, детальные тест-кейсы — в `docs/glpi/test-cases.md`.

## 2.1 Функциональные критерии

| № | Критерий | Как проверяется |
|---|---|---|
| A-01 | Любой сотрудник входит на https://sd.hofi.su по AD-логину без ручного заведения учётки | Вход 3 случайных сотрудников из разных подразделений |
| A-02 | Сотрудник подаёт заявку через портал не более чем в 3 клика + текст | Наблюдение за 3 пользователями без обучения |
| A-03 | Письмо на `<SUPPORT_MAILBOX>` создаёт заявку с правильным заявителем | Отправка письма с рабочей почты сотрудника |
| A-04 | Ответ на письмо-уведомление дописывается в ту же заявку | Ответ на уведомление, проверка отсутствия дубля |
| A-05 | Каждая из 15 категорий автоматически назначается на нужную группу | 15 тестовых заявок, по одной на категорию |
| A-06 | Заявка без подходящей категории попадает в `SD-L1`, а не «никуда» | Заявка по почте без категории |
| A-07 | Сроки реакции и решения проставляются автоматически и считаются по рабочему календарю | Проверки S-01…S-06 из `sla-matrix.md` |
| A-08 | Просрочка порождает уведомление руководителю ИТ | Заявка с намеренно коротким сроком |
| A-09 | Заявитель получает уведомления: регистрация, комментарий, решение | Полный цикл одной заявки |
| A-10 | Права разграничены: пользователь не видит чужие заявки, L1 не видит настройки | Проверки P-01…P-11 из `roles-matrix.md` |
| A-11 | Учётки `ext.*` и `svc.*` получают ограниченные профили автоматически | Заведение тестовой `ext.test` |
| A-12 | `Super-Admin` только у 2 поимённых учёток | Ревизия вкладки «Пользователи» профиля |
| A-13 | Заявка проходит полный жизненный цикл: Новая → Назначена → В работе → Решена → Закрыта | Сквозной прогон |
| A-14 | Отключение сотрудника в AD деактивирует учётку в GLPI, история заявок сохраняется | Тестовая учётка |

## 2.2 Эксплуатационные критерии

| № | Критерий | Как проверяется |
|---|---|---|
| A-15 | Cron отрабатывает: SLA, почта, уведомления запускаются по расписанию | Настройка → Автоматические действия, время последнего запуска |
| A-16 | Резервная копия БД снимается и **восстанавливается** на тестовом стенде | Пробное восстановление |
| A-17 | Нет циклов «уведомление → сборщик почты → новая заявка» | Сутки наблюдения за ящиком |
| A-18 | Инструкция пользователя опубликована и разослана | `docs/glpi/guides/`, рассылка |
| A-19 | Первая линия обучена и провела не менее 10 заявок на пилоте | Журнал пилота |
| A-20 | Конфигурация зафиксирована в `docs/glpi/config-log.md` | Ревью с `glpi-admin` |

## 2.3 Критерии цели (проверяются через 4 недели после запуска)

| № | Критерий | Целевое значение |
|---|---|---|
| A-21 | Доля обращений, поступивших через GLPI (портал + почта поддержки) | ≥ 80 % |
| A-22 | Доля заявок в категории «Другое» | ≤ 15 % (иначе дерево категорий пересматривается) |
| A-23 | Доля заявок, оставшихся без назначенной группы дольше 1 рабочего часа | 0 % |
| A-24 | Доля заявок с нарушенным сроком решения | ≤ 20 % (иначе пересматриваются времена SLA, а не наказываются исполнители) |

> A-24 намеренно мягкий. Первые цифры SLA — гипотеза; если просрочек
> много, сначала проверяется реалистичность нормативов.

# 4. Отложено (без срока)

Возврат к вопросу — по явному запросу бизнеса, не по инициативе проекта.

| Тема | Почему отложено | Что должно измениться, чтобы вернуться |
|---|---|---|
| Управление изменениями (`Change`) | Процесса изменений в компании нет. Это зафиксированное решение, а не пробел | Появится регламент изменений и орган согласования (CAB) |
| CMDB и связи конфигурационных единиц | Нет инвентаризации | Завершится R2-AST-01 |
| SSO / Kerberos | LDAP-аутентификации достаточно | Требование ИБ или жалобы на повторный ввод пароля |
| Управление финансами услуг, биллинг ИТ | Нет запроса | Переход на внутреннюю тарификацию ИТ |
| Не-ИТ услуги (АХО, HR) | Другие владельцы, другой проект | Решение о расширении ITSM за пределы ИТ |
| Мобильное приложение / чат-бот | Портал и почта закрывают каналы | ≥ 20 % обращений останутся вне GLPI после Релиза 1 |
| Миграция истории заявок | Решение не принято, см. RE-Q3 | Требование сохранить историю в едином интерфейсе |
| Мультиязычный интерфейс | Все пользователи русскоязычные | Появление иноязычных сотрудников |

# 5. Риски, влияющие на требования

| № | Риск | Влияние | Митигация |
|---|---|---|---|
| RR-1 | Cron не настроен или работает в режиме GLPI | SLA, почта и уведомления молча не работают | R1-INF-02 — блокирующее требование, проверка A-15 |
| RR-2 | Сотрудники продолжают писать в мессенджеры | Цель Релиза 1 не достигнута | R1-CH-07, план коммуникаций, метрика A-21 |
| RR-3 | ИТ-специалисты заводят заявки «задним числом» ради отчётности | Данные для Релиза 2 недостоверны | Проверка расхождения даты создания и реального обращения на пилоте |
| RR-4 | Владельцы услуг не согласованы к Релизу 2 | Каталог не наполняется | Шаг 4 в `service-catalog.md` — блокирующий, эскалация `glpi-pm` |
| RR-5 | Времена SLA заданы нереалистично | Массовая просрочка, недоверие к системе | Мягкий критерий A-24, пересмотр нормативов после 4 недель |
| RR-6 | Петля «уведомление ↔ сборщик почты» | Лавина заявок в первый день | Проверка A-17, разные адреса отправителя и приёмника |
| RR-7 | Права выданы слишком широко «чтобы заработало» | Потеря разграничения по сущностям | R-11, проверки A-10, A-12 |
| RR-8 | Решение по миграции принято поздно | Переделка справочников и учёток | RE-Q3, срок решения — до конца Релиза 1 |

## Открытые вопросы

| № | Вопрос | Вариант по умолчанию (принимается, если нет возражений) |
|---|---|---|
| RE-Q1 | Дата запуска Релиза 1 и состав пилотной группы? | **Пилот на ИТ-отделе 1 неделя, затем вся компания.** Без пилота первый день запуска станет пилотом для 500 человек. |
| RE-Q2 | Адрес общего ящика поддержки? | **`support@hofi.su`** (или `sd@hofi.su`). Нужен отдельный ящик, не личный и не существующий общий — иначе в GLPI попадёт вся старая переписка. |
| RE-Q3 | Мигрировать ли историю заявок из прежней системы? | **Нет.** Прежняя система переводится в режим «только чтение» на 6–12 месяцев, GLPI стартует с чистого листа. Миграция истории даёт мало пользы и отодвигает запуск на недели. Решение зафиксировать до конца Релиза 1. |
| RE-Q4 | Мигрировать ли справочники (пользователи, подразделения, активы)? | **Пользователи — из AD, а не из прежней системы. Активы — не мигрируем** (Релиз 1 их не использует). Подразделения — из AD при синхронизации. |
| RE-Q5 | Версия GLPI на инстансе — точно 10.x? | **Считаем 10.x.** Влияет на: наличие штатного конструктора форм и каталога услуг (есть в 11.x), поддержку Formcreator (нет в 11.x). Требует подтверждения до начала настройки. |
| RE-Q6 | Кто владелец системы GLPI со стороны заказчика? | **Руководитель ИТ.** Принимает Релиз 1, утверждает SLA, назначает владельцев услуг. Без единой точки приёмки этап не закрывается. |
| RE-Q7 | Останется ли телефон как канал приёма? | **Да**, с обязательным заведением заявки первой линией (R1-CH-06). Отмена телефона на старте вызовет сопротивление и обход системы. |
| RE-Q8 | Нужна ли форма обратной связи / оценка удовлетворённости? | **Не в Релизе 1.** GLPI поддерживает опрос удовлетворённости (Сущность → «Помощник» → «Опрос»); включаем в Релизе 2, когда процесс стабилен. |
| RE-Q9 | Что делать с открытыми заявками в прежней системе на момент запуска? | **Дорабатываются там же**, новые — только в GLPI. Перенос «хвоста» вручную создаёт двойной учёт. |
| RE-Q10 | Кто ведёт производственный календарь РФ ежегодно? | **Администратор GLPI**, задача в декабре (R2-OPS-01). Без владельца календарь устареет и SLA поедут. |
