# Ролевая модель, профили и права — HOFI (GLPI 10.x)

Статус: черновик на согласование
Область: Релиз 1 (минимальный контур) + план на Релиз 2

Объекты GLPI: `Profile`, `Profile_User`, `Entity`, `Group`, `Group_User`,
`AuthLDAP`, `RuleRight`, `RuleMailCollector`
Разделы интерфейса:
- Профили — **Администрирование → Профили**
- Назначение профиля пользователю — **Администрирование → Пользователи → <пользователь> → вкладка «Полномочия»**
- Сущности — **Администрирование → Сущности**
- LDAP — **Настройка → Аутентификация → Каталоги LDAP**
- Правила выдачи прав — **Администрирование → Правила → Правила назначения полномочий пользователю**

---

# 1. Ключевой принцип

**Профиль выдаётся не персоне, а связке «пользователь + сущность +
рекурсивность».** Одна и та же учётная запись может быть `Self-Service`
в одной сущности и техником в другой. Отсюда две типовые ошибки, которых
здесь избегаем:

- «дать всем Super-Admin, потом разберёмся» — разграничение по сущностям
  после этого не восстанавливается без ревизии всех учёток;
- выдавать профиль **рекурсивно** от корня всем подряд — рекурсивный
  профиль в корневой сущности означает доступ ко всем дочерним, включая
  те, что появятся позже.

Правило Релиза 1: рекурсивно от корня выдаётся **только** `Self-Service`
и профили двух администраторов. Всё остальное — точечно.

# 2. Роли Релиза 1 (четыре, плюс две служебные)

| Роль | Профиль GLPI | Базируется на | Интерфейс | Кол-во людей (оценка) |
|---|---|---|---|---|
| Обычный сотрудник | `Self-Service` (штатный, без изменений) | — | Упрощённый | 100–500 |
| Первая линия | `HOFI L1` (новый) | клон `Technician` | Стандартный | 2–4 |
| ИТ-специалист | `HOFI IT` (новый) | клон `Technician` | Стандартный | 4–10 |
| Администратор GLPI | `Super-Admin` (штатный) | — | Стандартный | **не более 2** |
| *служебная:* Подрядчик | `HOFI Contractor` (новый) | клон `Self-Service` | Упрощённый | по факту |
| *служебная:* Интеграции | `HOFI Service` (новый) | «с нуля», минимум прав | Стандартный (API) | 1–2 учётки |

> Штатные профили `Self-Service`, `Technician`, `Super-Admin` **не
> редактируются**. Любая правка — на клоне. Иначе обновление GLPI и
> сравнение с «как из коробки» становятся неразрешимыми.
> Клонирование: карточка профиля → «Дублировать» (кнопка «Клонировать»
> в действиях).

Роль «Наблюдатель/Руководитель» (штатный `Observer`) в Релизе 1 **не
выдаётся** — см. раздел «Отложено» в `requirements.md`.

# 3. Что каждой роли видно и не видно

## 3.1 Обычный сотрудник — `Self-Service`

| Может | Не может |
|---|---|
| Создать заявку (упрощённый интерфейс) | Видеть чужие заявки |
| Видеть свои заявки и заявки, где он наблюдатель | Назначать исполнителя, менять приоритет |
| Добавить комментарий и вложение к своей заявке | Видеть внутренние (приватные) комментарии техников |
| Подтвердить/переоткрыть решение своей заявки | Видеть активы, справочники, настройки |
| Читать опубликованные статьи базы знаний | Видеть отчёты и статистику |

Ключевые права (вкладка «Помощник» профиля):
- «Заявка» → «Создать» = Да; «Просмотр» = **«Свои»** (не «Все» и не «Группы»);
- «Следить за заявкой» / «Наблюдатель» = Да;
- «Добавить комментарий» = Да, «Добавить приватный комментарий» = Нет;
- «Одобрение решения» = Да;
- вкладка «Активы» — всё снято;
- вкладка «Администрирование» — всё снято.

Поле «Интерфейс» в карточке профиля = **«Упрощённый интерфейс»**.
Это и есть главный ограничитель: упрощённый интерфейс физически не
показывает меню активов, настроек и администрирования.

## 3.2 Первая линия — `HOFI L1`

Задача: принять, классифицировать, решить типовое, передать остальное.

| Может | Не может |
|---|---|
| Видеть **все** заявки своей сущности | Видеть заявки других сущностей |
| Создавать заявку от имени другого сотрудника | Удалять заявки (только закрывать) |
| Менять категорию, приоритет, срочность, влияние | Менять SLA вручную |
| Назначать заявку на группу или техника | Редактировать справочники и категории |
| Видеть карточку пользователя (телефон, кабинет, подразделение) | Редактировать пользователей и их права |
| **Читать** карточки активов (какой ПК у сотрудника) | Изменять/удалять активы |
| Писать приватные комментарии, задачи | Входить в «Настройка» и «Администрирование» |
| Создавать черновики статей БЗ | Публиковать статьи БЗ |

Ключевые права:
- «Заявка» → Просмотр = **«Все»**; Создать = Да; Изменить = Да;
  Удалить/Очистить = **Нет**;
- «Назначить заявку» = Да; «Взять заявку» = Да;
- «Приватные комментарии/задачи» = Да;
- «Активы» (Компьютеры, Мониторы, Принтеры, Телефоны) = **только «Чтение»**;
- «Администрирование → Пользователи» = **только «Чтение»** (нужно, чтобы
  видеть контакты заявителя; редактирование снять);
- «Настройка» — всё снято, включая «Справочники»;
- «SLA/Уровни обслуживания» = Нет;
- Интерфейс = **Стандартный**.

## 3.3 ИТ-специалист — `HOFI IT`

| Может | Не может |
|---|---|
| Всё, что `HOFI L1` | Удалять заявки |
| Изменять карточки активов (закрепление за пользователем) | Управлять профилями и правами |
| Публиковать статьи базы знаний | Менять SLA, календари, категории |
| Создавать и закрывать задачи по заявке | Настраивать правила и уведомления |
| Списывать трудозатраты | Входить в «Настройка» |

Отличие от `HOFI L1` — по сути только запись в активы и публикация БЗ.
Разделять сильнее в Релизе 1 не нужно: два почти одинаковых профиля
проще сопровождать, чем пять разных.

## 3.4 Администратор GLPI — `Super-Admin`

Полные права, включая «Настройка» и «Администрирование».

Ограничения, которые вводятся **организационно**, не правами:
- не более 2 человек, поимённо, в `docs/glpi/config-log.md` (ведёт `glpi-admin`);
- изменения конфигурации фиксируются в журнале конфигурации;
- личная повседневная работа с заявками ведётся под профилем `HOFI IT`
  (переключение профиля в правом верхнем углу), чтобы случайные правки
  конфигурации не проходили незаметно.

## 3.5 Подрядчик — `HOFI Contractor`

Клон `Self-Service` со снятыми правами на базу знаний и с назначением
**в конкретную сущность, не рекурсивно**. Нужен, чтобы внешние
исполнители могли подавать и вести заявки, не видя внутреннюю структуру.

Если подрядчик должен **решать** заявки, а не подавать — это отдельный
профиль на базе `HOFI L1` с ограничением по сущности и категориям.
Решение — открытый вопрос RQ-4.

## 3.6 Интеграции — `HOFI Service`

Для учётных записей почтового сборщика, REST API, GLPI Agent.
Права — строго под задачу, не «Super-Admin для удобства»:

| Учётка | Права |
|---|---|
| `svc.mail` | Заявка: Создать + Просмотр «Все»; больше ничего |
| `svc.api` | По факту интеграции; выдаётся после согласования с `glpi-integrator` |
| `svc.agent` | Инвентаризация: запись в активы; заявки — нет |

API-токен — в карточке пользователя, вкладка «Основное» → «Ключ API».
В репозиторий не попадает: в артефактах только `<API_TOKEN>`.

# 4. Матрица «роль × сущность × профиль»

Структура сущностей Релиза 1 — плоская: корневая сущность + при
необходимости одна дочерняя. Углублять до оргструктуры в Релизе 1 не
нужно (см. RQ-1).

| Роль | Сущность | Профиль | Рекурсивно | Способ выдачи |
|---|---|---|---|---|
| Обычный сотрудник (AD) | Корневая `HOFI` | `Self-Service` | Да | `RuleRight`, автоматически |
| Первая линия | Корневая `HOFI` | `HOFI L1` | Да | Вручную / `RuleRight` по AD-группе |
| ИТ-специалист | Корневая `HOFI` | `HOFI IT` | Да | `RuleRight` по AD-группе |
| Администратор | Корневая `HOFI` | `Super-Admin` | Да | **Только вручную**, поимённо |
| Подрядчик (локальная) | Дочерняя `HOFI / Подрядчики` | `HOFI Contractor` | Нет | Вручную при заведении |
| Интеграции (локальная) | Корневая `HOFI` | `HOFI Service` | Да | Вручную |

**Профиль по умолчанию** (галка «Профиль по умолчанию» в карточке
профиля) — `Self-Service`. Это определяет, что получит пользователь,
которому не подошло ни одно правило.

# 5. Два источника учётных записей: AD и локальные

## 5.1 Как GLPI их различает

Поле **«Метод аутентификации»** в карточке пользователя
(`Администрирование → Пользователи`):
- `LDAP-каталог <имя>` — учётка из AD;
- `База данных GLPI` — локальная учётка.

Это поле доступно как **критерий** в правилах назначения полномочий, и
на нём строится всё разделение.

## 5.2 AD — основной источник

Настройка: **Настройка → Аутентификация → Каталоги LDAP**.

| Параметр | Значение / плейсхолдер |
|---|---|
| Сервер | `<AD_HOST>`, LDAPS 636 (не 389 — иначе пароли ходят открытым текстом) |
| Base DN | `<AD_BASE_DN>` |
| Bind DN | `<AD_BIND_DN>` (сервисная учётка, права только на чтение) |
| Пароль | `<AD_BIND_PASSWORD>` — в репозиторий не попадает |
| Поле логина | `samaccountname` |
| Фильтр | исключить отключённые: `(!(userAccountControl:1.2.840.113556.1.4.803:=2))` |
| Синхронизация | автоматическое действие `syncLdapUsers`, ежедневно |

Детали интеграции — зона `glpi-integrator`, здесь фиксируются только
требования к правам.

Обязательные настройки поведения (**Настройка → Аутентификация →
Настройка аутентификации**):
- «Действие при удалении пользователя из LDAP» = **«Отключить
  пользователя (деактивировать)»**, не «Удалить». Уволенный сотрудник
  теряет доступ, но его заявки и история остаются.
- «Добавлять пользователя из внешнего источника без полномочий» =
  **Нет**. Иначе в базе копятся учётки без профиля, и непонятно, кто
  реально работает.

## 5.3 Правила назначения полномочий (`RuleRight`)

**Администрирование → Правила → Правила назначения полномочий пользователю.**
Порядок важен: правила выполняются сверху вниз, до первого с флагом
«Прекратить обработку» либо все подряд (накопительно).

| № | Правило | Критерии | Действия |
|---|---|---|---|
| 1 | AD — ИТ-администраторы | Метод аутентификации = LDAP `<AD>` **И** (LDAP) группа = `<AD_GROUP_IT_ADMIN>` | Профиль = `HOFI IT`, Сущность = корневая, Рекурсивно = Да |
| 2 | AD — Первая линия | Метод = LDAP **И** группа = `<AD_GROUP_SD>` | Профиль = `HOFI L1`, Сущность = корневая, Рекурсивно = Да |
| 3 | AD — Все сотрудники | Метод = LDAP **И** Base DN содержит `<AD_BASE_DN_USERS>` | Профиль = `Self-Service`, Сущность = корневая, Рекурсивно = Да |
| 4 | Локальные — подрядчики | Метод = «База данных GLPI» **И** логин начинается с `ext.` | Профиль = `HOFI Contractor`, Сущность = `HOFI / Подрядчики`, Рекурсивно = Нет |
| 5 | Локальные — сервисные | Метод = «База данных GLPI» **И** логин начинается с `svc.` | **Нет действия** (профиль выдаётся вручную) |

`Super-Admin` **не выдаётся ни одним правилом** — только вручную,
поимённо. Правило, выдающее Super-Admin по AD-группе, — это один
неверный член группы до потери контроля над системой.

## 5.4 Соглашение по именованию локальных учёток

| Префикс | Кому | Профиль | Пароль |
|---|---|---|---|
| `ext.` | Подрядчики, внешние исполнители | `HOFI Contractor` | Локальный, срок действия ограничен |
| `svc.` | Интеграции, почта, агент | `HOFI Service` | Локальный, только для интеграции |
| без префикса | **не заводить** | — | — |

Соглашение нужно именно потому, что критерий `RuleRight` по логину —
единственный простой способ автоматически развести локальные учётки.
Без префиксов придётся раздавать права вручную каждому.

## 5.5 Группы: AD или GLPI

Группы `SD-L1`, `IT-WS`, `IT-INF`, `IT-APP` (см. `categories.md`)
рекомендуется вести **в GLPI вручную**, а не синхронизировать из AD:
в Релизе 1 это 4 группы по 2–5 человек, а синхронизация групп из LDAP
добавляет ещё один источник отказа при запуске. Перевод на AD-группы —
кандидат в Релиз 2 (RQ-5).

# 6. Требования к настройке (для администратора)

| № | Требование | Объект GLPI | Раздел интерфейса |
|---|---|---|---|
| R-01 | Созданы профили `HOFI L1`, `HOFI IT`, `HOFI Contractor`, `HOFI Service` клонированием | `Profile` | Администрирование → Профили → Клонировать |
| R-02 | Штатные профили не изменялись | `Profile` | — (проверка) |
| R-03 | `Self-Service` помечен как «профиль по умолчанию» | `Profile.is_default` | Карточка профиля |
| R-04 | `Self-Service` и `HOFI Contractor` — интерфейс «Упрощённый» | `Profile.interface` | Карточка профиля |
| R-05 | `HOFI L1`: заявки «Все», активы «Чтение», настройка — нет | `Profile` права | Вкладки «Помощник», «Активы», «Настройка» |
| R-06 | `HOFI IT`: как L1 + запись в активы + публикация БЗ | `Profile` права | Те же вкладки |
| R-07 | `Super-Admin` назначен не более чем 2 поимённым учёткам | `Profile_User` | Администрирование → Профили → вкладка «Пользователи» |
| R-08 | Настроен LDAP-каталог по LDAPS с фильтром отключённых | `AuthLDAP` | Настройка → Аутентификация → Каталоги LDAP |
| R-09 | «Действие при удалении из LDAP» = деактивировать | Конфигурация | Настройка → Аутентификация → Настройка аутентификации |
| R-10 | Созданы 5 правил `RuleRight` в указанном порядке | `RuleRight` | Администрирование → Правила → Правила назначения полномочий |
| R-11 | Ни одно правило не выдаёт `Super-Admin` | `RuleRight` | — (проверка) |
| R-12 | Учётки интеграций имеют минимальный профиль, не `Super-Admin` | `Profile_User` | Администрирование → Пользователи |
| R-13 | Включено автоматическое действие синхронизации LDAP | `CronTask` `syncLdapUsers` | Настройка → Автоматические действия |

# 7. Приёмочные проверки прав (Релиз 1)

| № | Проверка | Ожидаемый результат |
|---|---|---|
| P-01 | Вход рядового сотрудника из AD | Упрощённый интерфейс, доступна форма заявки |
| P-02 | Сотрудник A открывает прямую ссылку на заявку сотрудника B | Отказ в доступе |
| P-03 | Сотрудник видит комментарий, отмеченный техником как приватный | Не видит |
| P-04 | Первая линия открывает раздел «Настройка» | Раздел отсутствует в меню |
| P-05 | Первая линия пытается удалить заявку | Действие недоступно |
| P-06 | ИТ-специалист меняет владельца компьютера в активах | Успешно |
| P-07 | Первая линия меняет владельца компьютера | Действие недоступно (только чтение) |
| P-08 | Учётка `ext.*` входит в систему | Профиль `HOFI Contractor`, видна только сущность «Подрядчики» |
| P-09 | Учётка отключена в AD, запускается синхронизация | Учётка в GLPI деактивирована, её заявки сохранены |
| P-10 | Новый сотрудник добавлен в AD, синхронизация | Автоматически получил `Self-Service`, вход работает без ручных действий |
| P-11 | Ревизия носителей `Super-Admin` | Ровно 2 поимённые учётки, сервисных среди них нет |

## Открытые вопросы

| № | Вопрос | Вариант по умолчанию (принимается, если нет возражений) |
|---|---|---|
| RQ-1 | Нужна ли структура сущностей по подразделениям/юрлицам? | **Нет в Релизе 1.** Одна корневая сущность + дочерняя «Подрядчики». Дробление сущностей — самое дорогое в откате решение; принимаем его на данных Релиза 1. |
| RQ-2 | Кто именно два администратора `Super-Admin`? | **Руководитель ИТ + один инженер.** Нужны ФИО до запуска — без этого некому принимать конфигурационные изменения. |
| RQ-3 | Какие AD-группы соответствуют первой линии и ИТ? | **Создать две новые AD-группы** специально под GLPI (`GLPI-SD`, `GLPI-IT`), а не переиспользовать существующие: их состав меняют вне ИТ. |
| RQ-4 | Подрядчики только подают заявки или решают их? | **Только подают** в Релизе 1. Право решать — Релиз 2, отдельный профиль с ограничением по сущности. |
| RQ-5 | Вести группы исполнителей в GLPI или синхронизировать из AD? | **В GLPI вручную** в Релизе 1 (4 группы). Синхронизация — Релиз 2. |
| RQ-6 | Нужен ли профиль «только чтение» для аудита/руководства? | **Не в Релизе 1.** Штатный `Read-Only` существует и включается за 10 минут, когда появится запрос. |
| RQ-7 | Разрешать ли первой линии создавать заявки от имени сотрудника? | **Да.** Иначе обращения по телефону и в мессенджерах не попадут в систему, и Релиз 1 не выполнит свою цель. |
| RQ-8 | Что делать с личными почтовыми ящиками ИТ, куда сейчас пишут? | **Настроить автоответ со ссылкой на портал** и постепенно отключить. Решение — совместно с `glpi-pm`, входит в план коммуникаций. |
