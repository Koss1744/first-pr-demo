# Каталог услуг — HOFI

Статус: **ШАБЛОН ДЛЯ ЗАПОЛНЕНИЯ ЗАКАЗЧИКОМ.** Не является результатом
обследования.
Область: Релиз 2. В Релизе 1 каталог услуг **не внедряется** — см. раздел 1.

> Всё, что ниже помечено `[ПОДТВЕРДИТЬ]`, — гипотеза аналитика на основе
> типового внутреннего ИТ, а не факт о HOFI. Услуга без подтверждённого
> владельца в GLPI не заводится.

---

# 1. Почему каталога услуг нет в Релизе 1

Приоритет заказчика — как можно быстрее прекратить приём заявок в
мессенджеры и на личную почту. Каталог услуг этой цели не помогает и
задерживает запуск:

- каталог требует поимённых владельцев услуг, а их согласование идёт
  неделями и вне ИТ;
- без владельцев каталог превращается в список названий, по которому
  заявку всё равно некому назначать — это ровно та ловушка, ради которой
  каталог и строят;
- пользователю на старте достаточно 15 понятных категорий
  (`categories.md`), чтобы заявка дошла до нужной группы.

Решение: **Релиз 1 работает на категориях, Релиз 2 добавляет каталог
услуг поверх них.** Данные Релиза 1 (реальное распределение заявок по
категориям за 4–8 недель) — основной вход для наполнения каталога.

---

# 2. Чем каталог услуг реализуется в GLPI

В GLPI 10.x **нет отдельного объекта «Услуга»** в ядре. Это принципиально
для планирования Релиза 2 — нужно выбрать носитель:

| Вариант | Объект GLPI | Плюсы | Минусы |
|---|---|---|---|
| A. Дерево категорий как каталог | `ITILCategory` (3-й уровень) | Ничего не ставить, уже работает | Нет полей «владелец услуги», «часы поддержки»; всё в комментарии |
| B. Плагин Formcreator | Формы + «Каталог услуг» плагина | Витрина услуг, разные формы под услуги | Внешний плагин; **не поддерживается в GLPI 11** |
| C. Объект «Приложения» (Appliances) | `Appliance` (Активы → Приложения) | Есть владелец, группа, связь с активами и заявками | Не витрина для пользователя, скорее реестр |
| D. GLPI 11 — встроенный каталог услуг и конструктор форм | ядро | Штатно, без плагинов | Требует обновления версии |

**Рекомендация (на подтверждение):** вариант **A + C** — дерево категорий
как витрина для пользователя, `Appliance` как реестр услуг с владельцами
и связями. Это не создаёт зависимости от Formcreator, которая сломается
при переходе на GLPI 11.

Окончательный выбор — открытый вопрос SCQ-1, решается вместе с вопросом
об обновлении до GLPI 11.

# 3. Структура записи об услуге

Поля, которые заказчик должен заполнить по каждой услуге. Колонка
«Где в GLPI» указывает, чем поле реализуется при варианте A+C.

| Поле | Обяз. | Смысл | Где в GLPI |
|---|---|---|---|
| Название услуги | Да | Формулировка от получателя, не от ИТ | `Appliance.name` / `ITILCategory.name` |
| Описание | Да | Что входит, что не входит | `Appliance.comment` |
| **Владелец услуги** | **Да** | ФИО. Отвечает за содержание и развитие услуги | `Appliance` → «Ответственный техник» (`users_id_tech`) |
| **Ответственная группа** | **Да** | Кому падают заявки | `Appliance` → «Группа ответственных» (`groups_id_tech`) + `ITILCategory.groups_id` |
| Получатели | Да | Все сотрудники / конкретные подразделения / только ИТ | Сущность + группы заявителей; ограничение видимости категории |
| Часы поддержки | Да | 5×9 / 24×7 / иное | `Calendar` → привязка через `SLM` |
| Класс SLA | Да | Базовый / повышенный / критический | `SLM` + `SLA`, правило `RuleTicket` по категории |
| Способ подачи | Да | Портал / почта / телефон | Канал приёма, см. `requirements.md` |
| Требуется согласование | Нет | Кто согласует выдачу | `TicketValidation` (валидация заявки) |
| Стоимость / бюджет | Нет | Если услуга тарифицируется | `Budget`, Управление → Бюджеты |
| Связанные активы | Нет | Серверы, ПО, лицензии | `Appliance_Item` |
| Поставщик / контракт | Нет | Для услуг на аутсорсе | `Supplier`, `Contract` |
| Статус | Да | Черновик / Действует / Выводится | `Appliance` → «Статус» (`states_id`) |

**Правило заведения:** услуга без заполненных «Владелец услуги»,
«Ответственная группа», «Часы поддержки» и «Класс SLA» в GLPI **не
создаётся**. Это защита от каталога, по которому невозможно работать.

# 5. Порядок наполнения каталога (Релиз 2)

| Шаг | Что делаем | Кто | Вход |
|---|---|---|---|
| 1 | Выгрузить распределение заявок Релиза 1 по категориям за 4–8 недель | `glpi-qa` / администратор | Заявки → сохранённый поиск, группировка по категории |
| 2 | Разобрать заявки из категории «Другое» — это ненайденные услуги | Аналитик | Отчёт по категории «Другое» |
| 3 | Свести список кандидатов в услуги, вычеркнуть то, чем никто не пользуется | Аналитик + руководитель ИТ | Шаблон разделов 4.1–4.4 |
| 4 | **Согласовать владельцев поимённо** | Руководитель ИТ | — |
| 5 | Заполнить часы поддержки и класс SLA по каждой услуге | Владельцы услуг | `sla-matrix.md`, раздел «Релиз 2» |
| 6 | Выбрать носитель каталога (вариант A/B/C/D, раздел 2) | Аналитик + администратор | Решение по версии GLPI |
| 7 | Расширить дерево категорий до 3-го уровня под услуги | Администратор | `categories.md` |
| 8 | Настроить дифференцированные SLA по услугам | Администратор | `sla-matrix.md` |

Шаг 4 — блокирующий. Пока владельцы не названы, шаги 5–8 не начинаются.

## Открытые вопросы

| № | Вопрос | Вариант по умолчанию (принимается, если нет возражений) |
|---|---|---|
| SCQ-1 | Чем реализуем каталог: категории, Formcreator, Appliances, GLPI 11? | **Вариант A + C** (категории как витрина + `Appliance` как реестр). Не создаёт зависимости от Formcreator, которая не переживёт переход на GLPI 11. |
| SCQ-2 | Планируется ли обновление до GLPI 11 в горизонте года? | **Считаем, что да.** Поэтому в Релизе 1 не вводим плагины, которые придётся выбрасывать. Требует подтверждения — от него зависит SCQ-1. |
| SCQ-3 | Входят ли в каталог не-ИТ услуги (АХО, HR, безопасность)? | **Нет.** Релизы 1–2 — только ИТ. Расширение на другие подразделения — отдельный проект с отдельными владельцами. |
| SCQ-4 | Есть ли услуги, оказываемые подрядчиками, с договорным SLA? | **Предполагаем, что есть** (1С, связь, печать). Нужен перечень договоров: без него внутренний SLA может оказаться жёстче, чем договор с подрядчиком. |
| SCQ-5 | Кто владелец услуги, если система куплена бизнесом без ИТ? | **Владелец — руководитель подразделения-заказчика**, ИТ — ответственная группа по инфраструктурной части. Фиксируем как правило, а не решаем по каждой системе. |
| SCQ-6 | Нужна ли услуга «Информационная безопасность» с ограниченной видимостью? | **Да, в Релизе 2** (связано с CQ-4 в `categories.md`). Требует отдельной группы и ограничения видимости категории. |
| SCQ-7 | Нужен ли процесс управления изменениями (Change) под каталог? | **Нет.** Отдельного процесса управления изменениями в компании сейчас нет — это зафиксировано как решение, а не как пробел. Заводить `Change` в GLPI ради ITIL не будем. |
| SCQ-8 | Кто утверждает каталог целиком? | **Руководитель ИТ**, одним документом, с указанием даты действия. Каталог без даты утверждения устаревает молча. |
