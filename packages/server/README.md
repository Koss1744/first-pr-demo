# @hofi/server - HOFI Auth Server

Internal MFA verification service: a multi-user, Active-Directory-backed TOTP
verification backend for gating employee logins, now also usable as a web SSO
identity provider. **Phase 1** (the `/api/v1` verification API) and **Phase 2**
(OIDC web SSO) are both implemented - see [Roadmap](#roadmap) for what's still
ahead.

Codes are generated by the user's phone authenticator app (Google/Microsoft
Authenticator, etc.) after scanning the QR from `/enroll/start`. This server
never generates or displays codes itself - it only verifies them.

## Setup

1. **Postgres**: create a database and a role with `CREATEDB`-free access to
   that one database (least privilege - it never needs to create/drop other
   databases in production, unlike the test suite which does).
2. **Root key**: `openssl rand -base64 32`, set as `HOFI_ROOT_KEY_V1`. This
   encrypts every stored TOTP secret - back it up somewhere safe (a secrets
   manager, not source control) and treat it as the crown jewels.
3. Copy `.env.example` to `.env`, fill in `HOFI_DATABASE_URL`,
   `HOFI_ROOT_KEY_V1`, and the `HOFI_LDAP_*` variables for your AD.
4. `npm run build` (from the repo root - builds `@hofi/core` first).
5. `npm run migrate -w @hofi/server` - applies the SQL migrations.
6. `npm run create-client -w @hofi/server -- credential-provider "Windows Credential Provider agent" verify`
   - prints a one-time API key. Each integration (Credential Provider agent,
     admin tooling) should get its own client/key with only the scopes it
     needs.
7. **Optional - web SSO (Phase 2)**: set `HOFI_OIDC_ISSUER`,
   `HOFI_OIDC_COOKIE_KEYS`, `HOFI_OIDC_CLIENTS` (one entry per company web
   app) and `HOFI_OIDC_JWKS` (`npm run create-oidc-jwks -w @hofi/server`).
   Leave all four unset to run Phase 1 only - the OIDC provider isn't mounted
   at all in that case. See [Web SSO (Phase 2)](#web-sso-phase-2) below.
8. `npm run start -w @hofi/server`.

## API

All endpoints are under `/api/v1` and authenticate via
`Authorization: Bearer <api-key>` (except `/healthz`). See
`src/routes/*.ts` for exact request/response shapes; summary:

| Endpoint | Scope | Purpose |
|---|---|---|
| `POST /enroll/start` | `enroll` | Look up an AD user, generate a secret, return an `otpauthUri`/QR for the user to scan |
| `POST /enroll/confirm` | `enroll` | Prove possession of the authenticator app before the secret goes live |
| `POST /verify` | `verify` | The endpoint everything else depends on - `{username, code}` -> `{result, reason?}` |
| `POST /admin/{unlock,reset,disable,enable}` | `admin` | Helpdesk operations |
| `GET /admin/audit` | `admin` | Filterable audit trail |
| `GET /healthz` | none | Liveness + DB check |

## Web SSO (Phase 2)

When `HOFI_OIDC_*` is set, this server also mounts a standard OpenID Connect
provider (via the [`oidc-provider`](https://github.com/panva/node-oidc-provider)
package) at the same origin, so any registered company web app can redirect
to it for login instead of rolling its own AD+MFA form.

- `GET /.well-known/openid-configuration` - standard OIDC discovery document.
- `/auth`, `/token`, `/userinfo`, `/jwks`, etc. - the standard OIDC/OAuth2
  endpoints, unmodified oidc-provider behavior.
- `/interaction/:uid/*` - the two-step login UI this package supplies:
  AD username/password (`Directory.verifyCredentials`), then a TOTP code
  (the same `verifyUser()` the `/verify` API and Phase 3's Credential
  Provider use). Consent is auto-granted - every client is a first-party
  company app an admin registered in `HOFI_OIDC_CLIENTS`, not a third party
  the end user needs to approve.
- Clients are statically configured via `HOFI_OIDC_CLIENTS` (a JSON array of
  [OIDC client metadata](https://github.com/panva/node-oidc-provider/blob/main/docs/README.md#clients)
  objects) - no dynamic client registration.
- Storage for oidc-provider's own models (sessions, grants, authorization
  codes, tokens, ...) is a generic Postgres-backed adapter
  (`src/oidc/adapter.ts`, migration `0005_create_oidc_store.sql`) - one table
  covers every model kind, since they all only need id/grant/user-code/uid
  lookup.

## Known risks (Phase 1, tracked deliberately)

- **`ldapjs` is unmaintained.** Its maintainer has publicly decommissioned
  the project (no further releases planned). It's still functionally
  complete for the bind+search usage here, and is isolated behind the
  `Directory` interface (`src/directory/`) specifically so it can be
  swapped for another implementation without touching any caller. Revisit
  before a production rollout - either vet it as acceptable for your risk
  tolerance, or replace `LdapDirectory` with an alternative.
- **API-key auth, not mTLS**, between this server and its clients (Credential
  Provider agent, admin tools). Reasonable for an internal network with no
  existing CA; upgrade path is isolated to `src/auth/api-key-auth.ts`.
- **Root key is a plain env var.** Fine for Phase 1 given the operational
  mitigations in place (0600 env file, dedicated low-privilege OS user); the
  envelope-encryption design (`src/crypto/envelope.ts`) leaves a clean seam
  to swap in a real KMS later without a schema change.
- **No self-service recovery.** A locked-out or lost-phone user needs an
  admin to call `/admin/unlock` or `/admin/reset` - there's no user-facing UI
  in Phase 1.
- **(Phase 2) Single JWKS key, from a plain env var.** Same tradeoff as the
  root key above (0600 env file, dedicated low-privilege OS user) - no
  automated rotation. Rotate manually by generating a new key, prepending it
  to `HOFI_OIDC_JWKS.keys` alongside the old one (old tokens keep verifying
  until they expire) and removing the old one on the next deploy after that.
- **(Phase 2) Login state between the password and TOTP steps is a signed
  cookie**, not server-side session storage (`src/oidc/pending-login.ts`) -
  keeps the interaction UI stateless/horizontally-scalable, but means anyone
  who steals that cookie within its 5-minute TTL has proven the AD password
  without yet needing the TOTP code. Mitigated by `httpOnly`/`secure`
  cookies and the short TTL; revisit if this ever needs to defend against a
  more capable on-path attacker.
- **(Phase 2) No dynamic client registration or per-client redirect URI
  admin UI.** `HOFI_OIDC_CLIENTS` is a static, redeploy-to-change list -
  fine for a handful of internal apps, not for self-service onboarding.

## Roadmap

- **Phase 2 (web SSO) - done:** an OIDC identity provider
  (`oidc-provider`) wraps the verification API so company web apps get MFA
  via standard OIDC, with AD password checked via
  `Directory.verifyCredentials`. See [Web SSO (Phase 2)](#web-sso-phase-2).
- **Phase 3 (Windows workstation logon):** a custom Windows Credential
  Provider calling `POST /verify`. This is native Windows/COM development
  requiring code-signing and a staged GPO rollout - out of scope for this
  package, and **must** ship with an offline/break-glass fallback so a
  server outage can't lock every workstation in the company at once.
