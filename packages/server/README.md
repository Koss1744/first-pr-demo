# @hofi/server - HOFI Auth Server

Internal MFA verification service: a multi-user, Active-Directory-backed TOTP
verification backend for gating employee logins. This is **Phase 1** of a
larger rollout - see [Roadmap](#roadmap) below for what's intentionally not
built yet.

Codes are generated by the user's phone authenticator app (Google/Microsoft
Authenticator, etc.) after scanning the QR from `/enroll/start`. This server
never generates or displays codes itself - it only verifies them.

## Setup

1. **Postgres**: create a database and a role with `CREATEDB`-free access to
   that one database (least privilege - it never needs to create/drop other
   databases in production, unlike the test suite which does).
2. **Root key**: `openssl rand -base64 32`, set as `HOFI_ROOT_KEY_V1`. This
   encrypts every stored TOTP secret - back it up somewhere safe (a secrets
   manager, not source control) and treat it as the crown jewels.
3. Copy `.env.example` to `.env`, fill in `HOFI_DATABASE_URL`,
   `HOFI_ROOT_KEY_V1`, and the `HOFI_LDAP_*` variables for your AD.
4. `npm run build` (from the repo root - builds `@hofi/core` first).
5. `npm run migrate -w @hofi/server` - applies the SQL migrations.
6. `npm run create-client -w @hofi/server -- credential-provider "Windows Credential Provider agent" verify`
   - prints a one-time API key. Each integration (Credential Provider agent,
     admin tooling, future OIDC handler) should get its own client/key with
     only the scopes it needs.
7. `npm run start -w @hofi/server`.

## API

All endpoints are under `/api/v1` and authenticate via
`Authorization: Bearer <api-key>` (except `/healthz`). See
`src/routes/*.ts` for exact request/response shapes; summary:

| Endpoint | Scope | Purpose |
|---|---|---|
| `POST /enroll/start` | `enroll` | Look up an AD user, generate a secret, return an `otpauthUri`/QR for the user to scan |
| `POST /enroll/confirm` | `enroll` | Prove possession of the authenticator app before the secret goes live |
| `POST /verify` | `verify` | The endpoint everything else depends on - `{username, code}` -> `{result, reason?}` |
| `POST /admin/{unlock,reset,disable,enable}` | `admin` | Helpdesk operations |
| `GET /admin/audit` | `admin` | Filterable audit trail |
| `GET /healthz` | none | Liveness + DB check |

## Known risks (Phase 1, tracked deliberately)

- **`ldapjs` is unmaintained.** Its maintainer has publicly decommissioned
  the project (no further releases planned). It's still functionally
  complete for the bind+search usage here, and is isolated behind the
  `Directory` interface (`src/directory/`) specifically so it can be
  swapped for another implementation without touching any caller. Revisit
  before a production rollout - either vet it as acceptable for your risk
  tolerance, or replace `LdapDirectory` with an alternative.
- **API-key auth, not mTLS**, between this server and its clients (Credential
  Provider agent, admin tools). Reasonable for an internal network with no
  existing CA; upgrade path is isolated to `src/auth/api-key-auth.ts`.
- **Root key is a plain env var.** Fine for Phase 1 given the operational
  mitigations in place (0600 env file, dedicated low-privilege OS user); the
  envelope-encryption design (`src/crypto/envelope.ts`) leaves a clean seam
  to swap in a real KMS later without a schema change.
- **No self-service recovery.** A locked-out or lost-phone user needs an
  admin to call `/admin/unlock` or `/admin/reset` - there's no user-facing UI
  in Phase 1.

## Roadmap

- **Phase 2 (web SSO):** wrap this verification API with an OIDC identity
  provider (planned: the `oidc-provider` npm package) so company web apps
  get MFA via standard OIDC, with AD password checked via
  `Directory.verifyCredentials` (already reserved in the interface, unused
  by Phase 1).
- **Phase 3 (Windows workstation logon):** a custom Windows Credential
  Provider calling `POST /verify`. This is native Windows/COM development
  requiring code-signing and a staged GPO rollout - out of scope for this
  package, and **must** ship with an offline/break-glass fallback so a
  server outage can't lock every workstation in the company at once.
